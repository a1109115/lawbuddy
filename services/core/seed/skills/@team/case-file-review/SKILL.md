# case-file-review — 案卷阅卷与证据分析

## 总览：菜单式路由

本 skill **不是**单向流水线。OCR 完成之后，根据用户意图走不同路径：

```
用户丢材料
  │
  ├─ Phase 1：OCR 转 Markdown（永远第一步）
  │
  ├─ Phase 2：路由节点
  │     ├─ 问身份（原告/被告？）→ 决定分析方向
  │     ├─ 问案由（如不确定则自动推断并建议）
  │     └─ 问意图（要做什么？）
  │           ├─ 「做证据清单」→ Phase 3→8（自动附带时效提示）
  │           ├─ 「完整阅卷」  → Phase 3→4→5→6→7→8
  │           └─ 「看矛盾」    → Phase 3→5
  │
  │      ⚠️ Phase 4.5 诉讼时效检查 = 全路径自动触发，不是独立选项
```

---

## 核心原则（不可跳过）

1. **OCR 是前提**：任何图片/PDF/扫描件必须先经 MinerU 转为 Markdown，再进行分析。不得对未 OCR 的材料直接下结论。
2. **每一条结论必须有源头**：标注来源 Markdown 文件的**可点击链接**（如 `[结算申请表 ← 核对](质保金申请_md/工程名/文件.md)`），方便直接打开 OCR 原文核对。
3. **矛盾点必须显式标注**：金额不一致、日期冲突、主体名称不同，必须在证据清单内用红字标出或在报告中按等级列出。
4. **不确定即标注**：OCR 提取不到的信息标注"（未提取到）"，优先用公式推算补上并注明"推算"。
5. **程序性自动检查（时效 + 管辖）**：只要提取到竣工日期 / 质保金到期日 / 催款日期，**必须自动判断时效状态并主动提示**；同时自动核对管辖条款（仲裁条款效力 / 专属管辖 / 协议管辖有效性）。都不需要用户开口问，不可跳过。
6. **交付前自检**：所有产出物必须通过三关校验（数量覆盖/质量扫描/逻辑一致性），不过关不交付。
7. **客观审查边界（用户立场，2026-08-30 确认）**：审查性输出（事实提取 / 矛盾检测 / 页数核对 / 形式要素核对）只记录材料原貌，**不自动输出三性评价等判断性内容**；质证立场由用户逐证据确认后提供（见被告路径）。法律评价仅出现在要件分析中，且必须援引案由知识库或材料原文。

### 以下三条为阅卷后新增铁律（第一性原理 + 对抗性审查结论）

8. **🔴 页序坐标铁律（先校准坐标，再谈内容）**：阅卷所有页码引用以**独立核验过的权威页序**为准，**严禁**直接采用 pipeline OCR 输出的 Markdown 顺序当作 PDF 页序。扫描 PDF 页序可能与 OCR 输出顺序偏移（某案偏移 2 页：死亡证明实际 P15，初判 P13）。执行 Phase 1.5 逐页核验后，metadata 必须存 `document_map`（权威页序），此后报告/时间轴/证据清单的页码一律引用它。
9. **🔴 关键字段双引擎交叉验证**：金额、日期、姓名、身份证号、死亡原因等**关键字段**，pipeline 单引擎识别结果**必须**经 vlm 复核确认（不一致 → 🔴 标注待人工复核，并附两引擎结果）。金额同时做**大小写交叉验证**（玖万元整 = 90,000）与**位数合理性校验**（存单出现"90,000,000"即位数异常）。单引擎未复核的关键字段在报告中必须标注验证状态，不得当作已确认事实直接输出。
10. **🔴 默认最小产出**：阅卷默认只产出「阅卷报告 + 时间轴」，**证据清单/质证意见/证据册等扩展产物一律等用户明确要求才生成**——阅卷阶段用户尚不知道哪些证据要进清单，过早生成导致认知过载（平铺 16 条"读死"教训）。产物形态也遵循此原则：证据清单默认**分组式**（3~4 条/组，≤5 组），平铺式仅当证据 ≤5 条且用户明确要求时使用。

## Phase 1：材料接收与 OCR 处理

### 1.1 文件分类

列出用户提供的所有文件，按类型分类：
- **程序文书**：起诉状、答辩状、判决书、裁定书等
- **证据材料**：合同、函件、付款凭证、发票、验收单、结算表、聊天记录等
- **附属材料**：证据目录、质证意见等

### 1.2 判断证据整理状态

检查材料是否已按工程/事项分组到子文件夹：
- **已分组**：每个子文件夹 = 一组证据，直接按组分析
- **未分组**：先通读判断事件结构，按时间/主体/事件自动建议分组方案

### 1.3 OCR 转换

使用 `MinerU Document Extractor` skill，对所有 PDF/图片/扫描件执行 OCR 转为 Markdown。

**工具优先级**：MinerU `extract`（鉴权 precision 模式）> `flash-extract`（免鉴权，限 20 页，大文件禁用）。

**extract 鉴权失败降级**（401 authenticate failed）：`extract` 报 HTTP 401 等鉴权错误时，先核对文件是否满足 flash-extract 限制（≤10MB / ≤20 页），满足则直接降级 `flash-extract` 并在输出中提示用户"extract token 已失效，已降级，建议重新 `mineru-open-api auth`"；超限则停下告知用户，不得静默用 flash 硬跑大文件（会触发低质量 tesseract 回退）。

**已有文本版优先**：案卷文件夹里若已有同文书的可读文本版（如项目早期整理的 .md/.docx），其**条款内容**以文本版为准（干净、无 OCR 噪声）；OCR 版仅用于核对**签章、手写签名、落款日期**等文本版不含的形式要素——两者是分工不是冗余。

**OCR 关键页视觉复核（条件触发）**：证据含手写要素（身份证号、签署日期、签名捺印）或 OCR 文本出现乱码/张冠李戴特征（如"乙刀：元""H期：2025年10月2日"）时，必须用 pymupdf 渲染该页为图片**目视核对**关键信息；纯打印体且文本干净的页面不需要渲染，避免无谓耗时。

**输出**：生成 `metadata.json`（记录每份文件的转换状态/引擎/页数/文档类型）+ 全部 `.md` 文件。

**OCR 完成后输出清单**，并列明引擎统计和 tesseract 残留数量。

### 1.4 OCR 失败处理（不可跳过）

实际操作中一定会遇到 OCR 不完整的情况：手写体识别失败、扫描质量极差、盖章遮挡关键字段。对这些文件按以下流程处理，**不得直接忽略、也不得假装已完整提取**：

1. **标记**：在 metadata.json 中记录该文件的 `ocr_status: "partial" | "failed"` 和 `failed_fields: [...]`（未能提取的具体字段）
2. **分级**：
   - 🔴 **关键字段失败**（如合同金额、验收日期、签章页）→ 列入"待人工复核"清单，在最终交付物中单独标识并红字标注
   - 🟡 **次要字段失败**（如开票日期、发票号码）→ 尝试用其他文书交叉补全；补不到则标注"（未提取到）"
   - 🟢 **格式性失败**（如段落排版错乱但文字已提取）→ 不影响分析，仅在 OCR 清单中备注
3. **推算兜底**：能通过公式推算的（如 申请剩余 = 合同金额 × 5%），推算后在证明目的中注明"推算"
4. **最终交付物必须包含 OCR 失败清单**（即使全部成功也要写"0 个失败"），放在证据清单末尾或阅卷报告附件

### 1.5 权威页序核验（🔴 强制）

> **背景教训**：某案中 pipeline OCR 输出顺序与 PDF 实际页序**偏移 2 页**（死亡医学证明实际在 P15，初判 P13），导致报告页码引用错误、用户核对原件时找不到证据。根源是**把 OCR 输出顺序当成了 PDF 页序**。

**执行步骤（不可跳过，任何多页 PDF/扫描件都要做）**：

1. **渲染逐页**：用 pymupdf 将每页渲染为 PNG（150dpi 足够识别标题，关键页另存 300dpi）
2. **逐页识别**：对渲染图逐张用 vlm 识别**每页首行标题/关键内容**（不要用 vlm 的 `--pages` 参数——该参数对多页 PDF 有偏移 bug，某案实测 4,36,37,38 实际映射到 3,35,36,37；**必须用渲染后的单页 PNG 逐张识别**）
3. **建立 document_map**：将识别结果与 pipeline 输出交叉比对，生成**权威页序表**（1-N 每页内容是什么），写入 metadata.json 的 `document_map` 字段
4. **页码引用一律引用 document_map**：此后报告、时间轴、证据清单中的页码（如 "P15"）均以权威页序为准，不得直接引用 pipeline 输出顺序
5. **关键页高精度复核**：含手写、金额、签章、死亡原因、身份证号的页面，用 300dpi 渲染 + vlm 复核关键字段（对应核心原则 9）
6. **🔴 降级路径（模型不支持读图 / vlm 不可用时强制）**：跳过逐页 vlm 核验，改「图块锚点法」建立 document_map：
   - 图块锚点：MinerU md 中图片引用 `![]()` 出现顺序 + 相邻文本标题（传票→起诉状→证据→附件）→ 推算每页归属
   - **勿试 dhash/MD5/尺寸匹配 MinerU 重编码图（实测全失败：MinerU 切块+重编码，指纹全变）**——直接放弃像素级匹配省 token
   - metadata 记 `page_verify_status: "单通道（图块锚点+内容自洽）"`，关键页（签章/快递单/手写）列入「待人工复核」，报告脚注注明"单引擎+单通道"

**metadata.json 必须包含**：
```json
{
  "total_pages": 38,
  "document_map": {"1": "手写签名页", "2": "身份证", "...": "..."},
  "page_verify_status": "vlm 逐页核验 38/38 | 关键页 300dpi 复核 N 页",
  "ocr_engine": "mineru extract (pipeline) + vlm 交叉验证"
}
```

## Phase 2：路由节点

OCR 完成后，**按顺序进行三次询问**（可合并提问）：

### 2.1 问身份

> "你是以原告还是被告的立场分析这些材料？"

- **原告** → 建构路径：梳理事实 → 确定案由 → 匹配要件 → 建证据链
- **被告** → 解构路径：分析起诉状 → 拆解要件 → 逐要件攻击证据漏洞 → 质证意见

### 2.2 问案由

> "本案的案由/请求权基础是什么？（如不确定，我会根据材料自动建议）"

- 用户指定案由 → 按该案由的构成要件分析
- 用户不确定 → 从材料中自动推断法律关系 + 案由建议，等用户确认
- **案由是开放的**（878 个第三级/第四级案由全覆盖）：一律从「案由知识库」（见「参考文档 → 案由知识库」）调取该案由的【案由适用要点】+【请求权基础规范】（含民法典/专门法逐条原文），作为定性、管辖、要件拆解、法条齐备性核对的**单一真源**。⚠️ 若案卷案由是**第四级子项**（stub 无独立正文），自动**回退读取父级第三级案由页面**获取权威内容（详见检索协议第 2 步）
- 要件拆解方法：拿到 wiki 的【请求权基础规范】后，按**"请求权基础 → 构成要件 → 抗辩事由"**逻辑自行拆解，填入下方要件拆解空白模板
- 案由为「建设工程施工合同纠纷」时 → **额外**加载 `references/domains/construction.md`，按建工专属争点（挂靠/转包/优先受偿权/工期/质保金性质/黑白合同）补充阅卷维度。案由为「股东知情权纠纷」时 → **额外**加载 `references/domains/shareholder-knowledge.md`（前置程序/查阅范围/律师费争点）。其他领域同理：新增专属争点时在 `references/domains/` 下加 `<案由>.md` 并在此加一行加载规则即可（可插拔）
- **domain 文件时效检查**：加载任何 `references/domains/*.md` 时，读取文件头部的 `<!-- last_verified: YYYY-MM-DD -->` 字段。距今超过 **6 个月**的，提示用户："本领域争点文件已 N 个月未核验，建议通过元典连接器重新核对法条是否有更新。"

**如果用户只需要做证据清单**（如已有明确的案由和完整的证据组），案由确认后可跳过完整阅卷直接进入 Phase 8。

**如果选择 ①（做证据清单）**：进入 Phase 8 前先执行 **8.0 生成前必问**——问清「模板来源」（用户自带模板 / 内置格式）、「清单形态」（分组式 / 平铺式）和「证明目的详略」（详细版 / 简略版），按用户答复生成，不自作主张选默认。

### 2.3 问意图

> "你希望我做什么？
> ① 直接生成证据清单（最常用）
> ② 完整阅卷分析（含时间轴、矛盾检测）
> ③ 只看矛盾点"

根据回答定路径：

| 用户选择 | 路径 | 最终产出 |
|---------|------|---------|
| ① 证据清单 | Phase 3→8 | 证据清单 .docx |
| ② 完整阅卷 | Phase 3→4→5→6→7 | 阅卷报告 + 时间轴（**不含证据清单**） |
| ③ 看矛盾 | Phase 3→5 | 矛盾点清单 |

> ⚠️ **证据清单默认不生成（用户确认）**：阅卷环节（无论完整阅卷还是矛盾检测）**默认不生成证据清单**——阅卷时尚未确定哪些证据要进入清单，过早生成会让用户读长清单"读死"。**只有用户明确说"生成证据清单/做证据清单"时才进入 Phase 8**（此时才执行 8.0 生成前必问：模板来源/清单形态/证明目的详略）。

**⚠️ 以上所有路径均自动附带诉讼时效检查（Phase 4.5），不论用户是否要求。**

### 2.4 元典连接器前置检查（⚠️ 每次阅卷必查，2026-08-30 新增）

进入 Phase 3 前，检查「华宇元典法律数据」连接器（yuandian MCP）是否可用：

- **已连接** → 关键法条（请求权基础 / 时效 / 管辖）**优先经** `yuandian_law_vector_search` 核验现行性（条号、修订年份、原文），与案由知识库【请求权基础规范】交叉比对；需要判例时用 `yuandian_case_vector_search`
- **未连接** → **不阻塞流程**，但必须在报告/交付物中提示："建议连接华宇元典法律数据连接器以核验法条现行性、检索超出案由知识库范围的法规（司法解释/部门规章/地方性法规）与案例；未连接时以案由知识库【请求权基础规范】为兜底。"

> 定位说明：元典是**法条权威性核验通道**（案由知识库可能存在 OCR 坑或法条过时，见 `synthesis/勘误与待确认.md` 与 procedural-checks 的 `last_verified` 机制）；未连接时 skill 不阻塞，保证公开分发可用性。

## Phase 3：事实提取与证据要素全量提取

从所有 Markdown 文件中**完整提取全部要素**，不做选择性的"只提质保金"式提取。每个文档类型提取其**包含的全部关键字段**。

### 3.1 证据编号

为每份证据分配编号（组内编号格式 `组-序号`，如 `1-1`、`2-3`）。

### 3.2 按文档类型的完整提取模板

| 文档类型 | 必须提取的全部字段 |
|---------|-------------------|
| 施工合同 | 签订日期（多个取最后一个）、合同金额、质保金条款（进度款比例 / 质保金比例 / 保修期）、发包方名称+信用代码、承包方名称+信用代码 |
| 结算申请表 | 合同金额、结算申请金额、竣工日期、已开发票金额、已支付金额、申请剩余金额、申请日期 |
| 请款通知书 | 应收金额、已收金额、本次申请金额、剩余质保金金额、申请日期 |
| 发票 | **全部**价税合计（多页 PDF 的每一页、同名文件的每一张）、开票日期、发票号码 |
| 验收表/报告 | 验收日期、验收结论（合格/不合格） |
| 质保金申请函 | 最终结算金额、已收到货款、申请质保金金额、日期 |
| 付款资料 | 本次付款金额、发票金额、日期 |
| 结算说明/清单 | 工程费、结算总额/合计金额 |
| 履约评估表 | 评估结论 |
| 施工照片 | 数量、拍摄内容简述 |

### 3.3 每项事实标注可点击来源

```
[合同.md ← 核对](质保金申请_md/5、外墙真石漆改造工程/外墙真石漆施工改造合同.pdf.md)
```

### 3.4 当事人身份校验

扫描所有材料中出现的全部主体名称，与起诉状/用户确认的当事人比对。出现不一致（如请款通知书抬头是"甲公司"而被告是"乙公司"）时，标记为需核对的当事人差异。

### 3.5 关键字段双引擎验证（🔴 对应核心原则 9）

**以下字段属于"关键字段"，pipeline 单引擎识别后必须经 vlm 复核**（不一致时报告内标注 🔴 待人工复核，并附两引擎结果）：

| 字段类别 | 示例 | 校验方式 |
|---------|------|---------|
| 金额 | 存单 43 万、墓穴 12,970 元 | 大小写交叉验证（玖万元整=90,000）+ 位数合理性（90,000,000 即异常） |
| 日期 | 死亡日期、注销日期、合同日期 | 两引擎比对 + 与相邻事件时间逻辑自洽 |
| 姓名 | 收据人（pipeline 误识"金某"→ vlm 确认"张某"） | 两引擎比对 + 与身份证明文件交叉 |
| 身份证号 | 18 位号码 | 校验码规则 + 与出生日期一致性（第 7-14 位） |
| 死亡原因/结论 | "无人在场的死亡" | 两引擎比对 + 标注出处页 |
| 手写/签章字段 | 签字、捺印、手写日期 | 300dpi 渲染 + vlm 复核，标注"待人工确认" |

**操作要求**：
- 提取后对每个关键字段标注验证状态：`✅ 双引擎一致` / `⚠️ 单引擎未复核` / `🔴 两引擎不一致待人工`
- 报告正文引用关键字段时，一律附带出处页码 + 验证状态

## Phase 4：法律关系与要件分析

### 通用要件拆解模板（适用于所有案由）

拿到 wiki 该案由的【请求权基础规范】后，按下方空白模板逐条拆解并匹配证据。**案由是开放的——wiki 878 个案由全部覆盖，不需要也不应该在本 skill 内硬编码任何案由的要件表。**

```
案由：________（来自 wiki 的权威定义）
请求权基础：________（wiki【请求权基础规范】逐条，含条号 + 原文）
管辖：________（wiki【案由适用要点】中的管辖段）

| 序号 | 构成要件 | 证明内容 | 对应证据 | 充分性 | 说明 |
|------|---------|---------|---------|--------|------|
| 1    | ____    | ____    | ____    | ✅/⚠️/❌ | ____ |
| 2    | ____    | ____    | ____    | ✅/⚠️/❌ | ____ |

常见抗辩：________（从 wiki 法条和 domain 文件的"常见抗辩/红旗"段提取）
```

**充分性判定标准**：
- ✅ 充分：有直接证据证明，证据来源明确
- ⚠️ 部分充分：有间接证据或部分证明，但存在缺口
- ❌ 缺失：完全没有对应证据

### 原告路径 — 建构

1. 确定案由（用户指定或自动推断）
2. 从 wiki 调取该案由的【请求权基础规范】，按上方空白模板拆解构成要件
3. 逐要件匹配证据（表格：构成要件 | 对应证据 | 充分性 | 说明）
4. 标注证据不足之处，给出补证建议

### Phase 4+：法规检索（仅完整阅卷路径，可选）

在要件分析完成后，可选地通过元典连接器补充法律依据原文。

**三条路径，按可用性优先**：

1. **元典已连接** → 调 `yuandian_law_vector_search` 检索本案涉及的法条原文，嵌入要件分析表
2. **元典未连接** → **不强制安装**。直接使用案由知识库的【请求权基础规范】（已含民法典/专门法逐条原文）作为法条来源，这已能满足绝大多数案件的要件分析
3. **用户主动选择安装** → 提示："你尚未安装「华宇元典法律数据」连接器，如需检索超出案由知识库覆盖范围的法规（如司法解释、部门规章、地方性法规），可前往连接器市场安装。"

要件分析表格式（三种路径通用）：`构成要件 | 对应证据 | 法律依据 | 充分性` 四列。

此步骤不会打断其他路径（证据清单快速路径、矛盾检测等），仅完整阅卷时触发。

### 被告路径 — 解构

1. **诉状解构**（先于要件拆解）：
   - **诉请结构分析**：拆解诉讼请求的逻辑关系——主请求与附属请求的依存关系（如本金与利息、返还与利息起算日）、每项请求金额的计算依据（合同条款/行业标准/司法解释，注明出处）、诉讼费/保函费/律师费承担主张的依据
   - **案件事实梳理**：按时间顺序列出诉状陈述的关键法律行为；标注诉状陈述中的逻辑漏洞（前后矛盾、无证据支撑的断言）——只列出"该陈述缺乏对应证据/与证据 X 矛盾"，**不做三性评价**（见核心原则 7）
   - 梳理结果单列一节写入被告报告（模板第二章），作为后续逐要件攻击的事实底稿
2. 从对方起诉状中提取案由 + 诉讼请求
3. 从 wiki 调取该案由的【请求权基础规范】，按上方空白模板拆解案由为构成要件
4. **逐要件攻击**：

```
要件：合同成立
├── 对方有证据吗？→ 有（施工合同）
│   └── 该证据本身有瑕疵吗？→ 检查签名/日期/金额
├── 与己方证据是否矛盾？→ 如存在矛盾，标注矛盾点
└── 攻击结论：该要件【成立/存疑/不成立】

要件：质保金到期
├── 对方有证据吗？→ 有验收报告
│   └── 验收日期是否真实？保修期是否确已届满？
├── 是否已过诉讼时效？→ 检查
└── 攻击结论：该要件【成立/存疑/不成立】
```

4. 汇总攻击要点，进入 **Phase 4.6 质证意见互动**（被告路径自动进入）

### Phase 4.6：质证意见互动（⚠️ 被告路径自动）

质证是立场判断，skill **不代用户做判断**——逐证据与用户互动确认立场后再生成（对应核心原则 7）。流程：

1. **出清单**：逐证据列出客观情况（证据名称、证明目的、可观察的事实：有无原件/签名/与其他证据的关系），**不带三性结论**
2. **问立场**：向用户逐证据问："该证据你方是认可 / 部分认可（认可什么不认可什么）/ 不认可？"——用户答复即质证立场，允许批量回答（"1-3 都认可，1-5 不认可"）
3. **生成**：仅对用户标记"不认可/部分认可"的证据生成质证意见，从法律逻辑、证据链条、合理推论三个维度展开反驳；**用户标记"认可"的证据一律不生成**，也不主动建议用户不认可
4. 输出格式：逐证据一段，含"对方证明目的 → 我方立场（用户确认的）→ 反驳意见"，写入被告报告第七章

### Phase 4.4：对抗推演（⚠️ 完整阅卷路径强制，证据清单快速路径可选）

真实庭审是回合制——阅卷不能只看"我这方说得通"，还要模拟对方的反击。本环节针对原告/被告分别做对抗推演：

**原告路径 — 自我压力测试**：

```
模拟被告最可能的 3 个抗辩点：
├── 抗辩 1：____（如"诉讼时效已过"/"工程质量不合格"/"挂靠致合同无效"）
│   ├── 我方现有证据能否反驳？→ 能 / 部分 / 不能
│   ├── 反驳所需的关键证据是否已在案卷中？→ 在 / 缺
│   └── 风险等级：🔴高 / 🟡中 / 🟢低
├── 抗辩 2：____
│   └── 同上
└── 抗辩 3：____
    └── 同上

对抗推演结论：
- 需补强的证据：____
- 可能需要调整的诉讼请求：____
- 开庭预案要点：____
```

**被告路径 — 预判原告反击**：

```
我方抗辩主张：____
├── 原告最可能的反击 1：____
│   ├── 我方是否有应对证据？→ 有 / 缺
│   └── 应对策略：____
├── 原告最可能的反击 2：____
│   └── 同上
└── 原告最可能的反击 3：____
    └── 同上

对抗推演结论：
- 我方抗辩的最大软肋：____
- 需预备的反驳证据：____
- 庭审中可能被对方翻盘的点：____
```

抗辩点的提取来源：① 案由知识库该案由的【常见抗辩】段；② domain 文件（如 construction.md）的【常见红旗】段；③ Phase 5 矛盾点检测中发现的、可能被对方利用的矛盾。

### Phase 4.5：程序性专项检查（⚠️ 强制自动，不可跳过）—— 时效 + 管辖

> **法规依据单一真源**：`references/procedural-checks.md`（含民法典/民诉法/仲裁法/票据法/海商法等法条**原文**，2026-08-30 经元典核对现行条号）。执行本检查时直接引用该文件，不重复检索；注意其中的版本警示——**仲裁法已于 2025 修订（2026-03-01 施行）条号重排、海商法 2025 修订（2026-05-01 施行）**。

**本检查在以下任何路径中自动触发，不需要用户开口要求：**
- 做证据清单 → 自动提示
- 完整阅卷 → 自动提示
- 看矛盾 → 自动提示

#### 4.5.1 诉讼时效检查

只要材料中能提取到竣工日期/质保金到期日/催款日期，就**必须**自动判断时效状态。这是案件中最容易忽视的问题。

### 时效规则按案由路由（不统一套民法典 188 条）

| 案由类型 | 时效规则 | 法律依据 |
|---------|---------|---------|
| 一般民事（合同/侵权/建工/借贷/买卖…） | 3 年，自权利人知道或应当知道权利受损害及义务人之日起算 | 《民法典》第 188 条 |
| 时效中断 | 催告/起诉/承诺履行 → 时效重新起算 | 《民法典》第 195 条 |
| 国际货物买卖 / 技术进出口 | **4 年** | 《民法典》第 594 条 |
| 海上货物运输 / 海商 | **1 年**（《海商法》另有规定的从其规定） | 《海商法》（2025 修订）第 284 条 |
| 票据权利 | 汇票/本票对出票人承兑人 **2 年**；支票出票人 **6 个月**；对前手追索 **6 个月**；再追索 **3 个月**——均为**除斥期间**，权利消灭，不中断不延长 | 《票据法》第 17 条 |
| 仲裁 | 适用诉讼时效规则，但仲裁规则另有期限的从其规定 | 各仲裁规则；《民法典》第 198 条 |
| 人身损害（含产品责任） | 3 年（民法典侵权），但**产品责任最长 10 年**除斥期间 | 《民法典》第 188、195 条；《产品质量法》第 45 条 |
| 股东知情权等社员权/共益权 | **主流观点不适用诉讼时效**（社员权非债权请求权，民法典196条第4项兜底）；备位观点 3 年自公司拒绝之日起算——报告同时列两种口径，时效抗辩是否主张由用户决定 | 《民法典》第 188、196 条 |

**执行步骤**：

1. 从案卷识别具体案由 → 按上表选定适用的时效规则
2. 提取竣工/验收日期 + 保修期 → 计算质保金/款项到期日
3. 提取催款/请款日期 → 判断诉讼时效中断时点（《民法典》195 条）
4. 按适用时效期限判断是否已过；**特别注意除斥期间（如票据权利、产品责任 10 年）不适用中断**

**输出时效判断表**：

| 工程 | 适用时效规则 | 到期日 | 最近催款日 | 时效至 | 状态 |
|------|------------|--------|----------|--------|------|
| 车道雨棚 | 民法典 188 条（3 年） | 2018-04-30 | 2026-04-27 | 2029-04-26 | ✅ 未过 |

#### 4.5.2 管辖检查

从起诉状/合同中提取管辖相关信息，按以下顺序机械核对（只对照法条记录客观结论，不做策略建议）：

| 检查项 | 核对内容 | 法律依据 | 输出 |
|--------|---------|---------|------|
| 仲裁条款 | 合同有无仲裁条款？约定的仲裁机构名称是否明确（"由仲裁委员会仲裁"这类约定不明 → 达不成补充协议则无效）？纠纷性质是否属于可仲裁范围？ | 《仲裁法》（2025 修订）第 27、28、29 条 | 有效仲裁条款 → 提示"本案应仲裁，法院受理存在障碍"；无效/无 → 继续 |
| 专属管辖 | 案由是否涉不动产纠纷（不动产所在地）、港口作业（港口所在地）、继承（被继承人死亡时住所地/主要遗产所在地）？涉外案件另核法人设立解散清算/决议效力、知产有效性、三类涉外合同（民诉法 279 条） | 《民事诉讼法》第 34、279 条 | 命中 → 记录"受理法院 vs 法定专属管辖法院"，不一致即红字标注 |
| 协议管辖 | 合同有无协议管辖条款？约定的连接点（被告住所地/合同履行地/签订地/原告住所地/标的物所在地等）是否与争议有实际联系？是否违反级别管辖/专属管辖？ | 《民事诉讼法》第 35 条 | 有效 → 核对受理法院是否在约定范围内；无效 → 按法定管辖核对 |
| 法定管辖兜底 | 无仲裁无协议时：被告住所地/合同履行地（合同案由）核对受理法院是否正确 | 《民事诉讼法》第 22、24 条 | 记录核对结论 |

**输出管辖核对表**（并入报告，与时效判断表并列）：

| 检查项 | 案卷情况 | 核对结论 | 法律依据 |
|--------|---------|---------|---------|
| 仲裁条款 | 合同第 X 条约定 XX 仲裁委员会 | 机构明确，有效 | 仲裁法（2025 修订）27 条 |
| 专属管辖 | 不涉及（案由=民间借贷） | 不适用 | — |
| 受理法院 | XX 区法院（被告住所地） | ✅ 正确 | 民诉法地域管辖 |

- 提取不到管辖条款时如实标注"（未提取到）"，不臆断
- 判断为"受理法院可能错误"时只红字提示核对结论，**管辖异议是否提起由用户决定**——skill 不出策略建议（核心原则 7）

#### 4.5.3 起诉时间核验

**起诉状落款日期 vs 传票案号年份/开庭时间不一致**时（如落款 2018-12-15、案号 (2020)…1673 号），标注 🔴 待人工核对**实际立案时间**——涉时效中断起算与"撤诉后重诉"判断。核对来源：传票案号年份、立案通知书、送达回证；报告时效表中注明"以实际立案时间为准"。

## Phase 5：矛盾点检测与金额交叉校验

### 5.1 五类矛盾检测

按 `references/contradiction-rules.md` 执行：
- 时间矛盾、事实陈述矛盾、**金额/数量矛盾**、主体矛盾、证据链断裂

### 5.2 金额交叉校验（新增，必须执行）

同一项目内，合同金额 / 结算申请表金额 / 发票合计 / 请款通知书金额 / 已付金额 / 质保金金额 须做交叉比对：

- 结算表自洽：已付 + 申请剩余 = 合同金额
- 请款勾稽：请款金额 = 合同金额 − 质保金（正常），否则标记异常
- 发票合计 vs 结算表自述已开发票金额
- 不一致用 **红字（#CC0000）** 在证据清单内标注，不同步开文档

### 5.3 矛盾等级

| 等级 | 标识 | 处理 |
|------|------|------|
| 🔴 严重 | 致命矛盾 | 证据清单红字 + 报告突出显示 |
| 🟡 一般 | 普通矛盾 | 报告列出 |
| 🟢 轻微 | 可解释差异 | 报告备注 |

## Phase 6：时间轴生成

### 6.2 生成方式

- 悬停展开详情（金额、当事人、来源文件）

## Phase 7：阅卷报告生成

### 报告通用要求（🔴）

1. **1.1 材料清单表必须含「证明目的简释」列**（用户明确认可的改进）：表格列为 `页码 | 内容 | OCR 状态 | 证明目的简释`，每份证据一句话点明"该证据要证明什么"——读者扫一眼就能定位证据在案件中的作用，不用逐页读全文。核心证据（死亡证明/大额凭证/不动产证）可加粗。
2. **所有关键字段（金额/日期/姓名/死亡原因等）引用时附带验证状态**：`✅ 双引擎一致` / `⚠️ 单引擎未复核` / `🔴 待人工复核`（对应核心原则 9）。
3. **所有页码引用以 Phase 1.5 权威页序为准**（对应核心原则 8）。
4. **报告末尾必须附「待人工确认项」清单**：手写页、疑似 OCR 误读字段、当事人身份疑点等，逐条列出页码 + 原因（对应核心原则 4）。

### 报告模板

`templates/review-report-complaint-evidence.md`（原告）/ `templates/review-report-defendant.md`（被告，含诉状解构/要件攻击/程序性检查/质证意见/答辩策略）/ `templates/review-report-evidence-only.md`（纯证据清单）——**结构以模板文件为准**，生成时直接套用。

## Phase 8：证据清单生成（可独立调用）

证据清单跳过 Phase 4-7，从事实提取直接生成可直接立案使用的 Word 文档。

### 8.0 生成前必问：模板来源 + 清单形态 + 证明目的详略（⚠️ 用户明确要求）

生成证据清单**之前**，必须先向用户确认三个问题（一次问完，不要自作主张选默认）：

**问题 1 — 模板来源**（内置格式未必是用户习惯的格式）：

> "你有没有自己习惯的证据清单模板（Word 文档）？有就发我，我按你的模板填；没有就按我的标准格式来。"

- **用户提供模板** → 生成时**完全沿用模板**：列头、编号风格、字体字号、表格样式、标题层级一律以模板为准，只把内容填进模板结构；模板与内置默认格式冲突时**以模板为准**，不得"顺手纠正"用户的格式
- 模板本身已能看出清单形态（分组式/平铺式）时，直接按模板的形态走，问题 2 不用再问（证明目的详略仍要确认）
- 模板填空实现参考 `docx-template-filler` skill（python-docx 直改 run.text，格式 100% 保留），不重排不重设样式
- **无模板** → 用内置标准格式，继续问题 2、3

**问题 2 — 清单形态**：证据清单有两种类型，问用户要哪种？

| 类型 | 编号方式 | 适用场景 | 特征 |
|------|---------|---------|------|
| **A. 分组式** | 组标题 + 组内编号 `组-序号`（1-1, 1-2…），每组一张小表 | 证据多的复杂案件（如多工程建工案） | 层次清晰，每组围绕一个事实/工程 |
| **B. 平铺式** | 单表，编号 `证据一/二/三…`（或 1→N），不分组 | 证据少的简单案件（3~5 条以内） | 简洁直接，同类的付款+回单可合并为一条 |

> ⚠️ **默认分组式**：证据超过 5 条时**默认分组式**（3~4 条/组，最多 5 组），不再默认平铺——平铺式 16 条长清单会让读者"读死"。平铺式仅当**证据 ≤5 条且用户明确要求**时使用。此偏好已写入核心原则 10。

- 证据 ≤5 条时倾向建议平铺式，但**仍以用户答复为准**（用户可能口头说"就分 3 条证据"——这就是平铺式的明确指示，直接照做，不要自行再拆组）
- 平铺式允许同类证据合并为一条（如"付款记录（微信转账记录、银行回单）"一条内含两类凭证），证明内容分段写清各凭证各自证明的事实
- ⚠️ **分组式每组必须配组证明目的**（用户要求）：分组式的每个组主标题下方、证据表格之前，加一段**本组证据的证明目的**（如"本组证据共同证明：……"），先总后分——组段概括本组证据共同证明的核心事实及其在诉请中的作用，表内每条证据再各自展开；平铺式无组标题，不需要此段

**问题 3 — 证明目的详略**：每条证据的"证明内容"写多详细？

- **详细版**：逐要素完整列明（日期、金额、条款、账户等全部关键字段 + 与诉讼请求的对应关系），适合需要向法院充分展示证据链的案件
- **简略版**：一句话点到为止（如催款记录只写"证明原告持续向被告催款"），用户可能对某些组单独指定从简——允许同一条清单内详略混用（用户指定哪条简哪条就简）

**确认后按所选形态生成**。无模板时列头为：编号 | 证据名称 | 证据来源 | 证明内容 | 页数；**用户提供模板时列头以模板为准**（模板列头缺"证据来源/页数"等法院惯例列时，提醒用户是否补上，用户说不补就不补）。

### 8.1 格式标准

- 分组式：工程序号 1→N 顺排；证据编号：组内编号 `组-序号`（如 1-1, 1-2）；组证明目的规则见 8.0
- 平铺式：编号 `证据一/证据二…` 或 1→N 顺排，单表呈现，无组标题故无组证明目的段
- 页码：分组式组内逐页累加 `组号-起始~组号-终止`（如 1-1~1-13）；平铺式直接写该条证据页数（如 4、1、2）
- 列：编号 | 证据名称 | 证据所要证明的事实 | 页码（**用户提供模板时以上各条以模板为准**，本节为无模板时的内置默认）
- 证据名称：去扩展名、去数字编号前缀、去"已盖章"/合同编号标记
- 证明目的：不写合同编号；每个文书完整列出该文书包含的全部工程款要素（详略按 8.0 问题 3 用户选择）

### 8.2 证明目的模版

**组证明目的（分组式专用，置于每组标题与表格之间）**：本组证据共同证明：________（一句话概括本组证据整体证明的核心事实，如合同关系及退款担保约定成立 / 款项已支付且仅部分退还 / 原告持续催款导致时效中断），是原告诉请________（对应诉请项）的依据。

**施工合同**：证明原、被告签订施工合同（签订日期），约定合同金额 X 元，保修期 X 年，进度款 X%，剩余 X% 为保修金——原告诉请的合同依据。

**结算申请表**：证明：合同金额 X 元，竣工日期 X，已开发票 X 元，已支付 X 元，申请剩余 X 元——原告诉请金额的计算依据。

**请款通知书**：证明：应收 X 元，已收 X 元，本次申请 X 元，剩余质保金 X 元——催告及诉讼时效中断的证明。

**发票**：证明原告已就本工程向被告开具增值税发票，合计金额 X 元——原、被告间工程款具体金额的佐证。

### 8.3 自检（三重，内置在生成脚本中，不通过不存盘）

1. **数量校验**：`metadata 文件数 ≈ 证据清单行数`（多张发票/验收单合并为一行属正常，差值必须可解释）
2. **质量扫描**：逐行检查是否有空白证明目的/模板文字残留
3. **逻辑一致性**：跨文书金额交叉比对，不一致处红字标注
4. **Dtype 覆盖**：各类"其他材料"按文件名关键词做二次分类（DTYPE_OVERRIDE 字典），确保无遗漏
5. **重复证据排查**：同一证据多格式（如发票.pdf 是两张 JPG 的合并版）、照片/施工照片 PDF 内部完全重复页，都须先识别再定页数，否则页码虚高（感知哈希筛候选 + 完整像素 MD5 精确确认）
6. **页数核对口径**：zip 内图片数可能 ≠ 清单页数（如清单写 7 页实际解压 6 张）；照片 PDF 去重后页数变化须同步更正清单页码
7. **🔴 诉请-证据对照（快速路径唯一保留的要件检查）**：起诉状（或用户主张）的**每项诉请、每个金额组成**（本金 / 利息起算日 / 律师费 / 担保责任……）必须能在清单中找到对应证据行。找不到的**红字提示用户补证**——诉请金额是拆出来的（如返还 90,000 = 已付 100,000 − 已退 10,000），支撑拆解的原始凭证（10 万转账记录）缺失时，返还请求权和利息起算日会**同时悬空**，这不是"证据充分性问题"而是"诉请能否成立问题"。本案教训：卷内只有 1 万退款凭证，缺 10 万付款凭证。
8. **脚本来源**：简单案件（平铺式、3~5 条）可手写生成脚本，但应先查看 `scripts/generate_evidence_list.py` 确认不适用再手写；自检断言值（行数/页数）从实际数据推导，不得拍脑袋硬编码后靠报错改数

### 8.4 时间补充

证据清单"证明事实"里只有金额、缺时间的组（如某些零星改造工程只有结算金额无日期），从证据文件里找时间补入证明事实（结算申请表"已于 YYYY 年完成"、结算单/报价单"YYYY 年 M 月—M 月"、请款通知书落款日期、照片水印时间）。**只写文件里真实提取到的时间，月日空白时精确到"年"，绝不编造具体日期。**

2. 打开对应分卷 `parts-merged/{file}`，**grep 锚点** `{anchor}`（如 `## 267_股东知情权纠纷`）定位，读取该案由段落（仅几 KB，不读全卷）：
   - **第三级案由**（anchor 如 `## 102_赠与合同纠纷`）→ 直接提取其【案由适用要点】【请求权基础规范】
   - **第四级子项 stub**（anchor 如 `## 102-1_公益事业捐赠合同纠纷`）→ 段落内标注父案由编号，**回退读取父级锚点** `## {父编号}_` 对应的第三级案由段落取权威内容
3. 与案卷材料比对：案由定性是否准确、管辖依据、请求权基础法条是否齐备
4. 注意 `references/cause-of-action-wiki/synthesis/勘误与待确认.md` 中标注的已知 OCR 问题（如 180 误作"低毁"）

> 知识库更新：源 wiki 有更新时，重跑 `scripts/merge_cause_wiki.py <wiki根目录> references/cause-of-action-wiki` 重新生成分卷。
> 发布/共享本 skill 前的打包步骤（脱敏复扫、文件数检查）→ 见 `references/PUBLISH-CHECKLIST.md`（按需加载，日常阅卷不读）。
