# 证据后处理（增量编辑 / 编排打页码 / 压缩拆分）— 按需加载

> **本文件为低频后处理流程**，不进 SKILL.md 主流程。触发条件：证据清单定稿后的插入/删除/重编号（Phase 9）、证据册编排打页码（Phase 10）、法院上传超 100MB 压缩拆分（Phase 11）。需要时读取本文件执行。

## Phase 9：证据清单增量编辑（后期补正/插入/删除）⚠️ 新增 v2.6.0

证据清单不是一次成型的——后期经常需要补漏、插入遗漏的工程组、或删除不再使用的组。本 Phase 提供**不推倒重来**的增量编辑能力。

### 9.0 铁律（踩坑总结，不可违反）

1. **先备份，再动手。** 操作前必须 `shutil.copy2` 备份原文件，绝不直接改唯一副本。
2. **读全量数据再做。** 不要试图用 XML 插入的方式局部修补——python-docx 的 `deepcopy` + `body.insert` 对复杂表格极易产生重复元素和不可逆损坏。正确做法：**读出现有所有组的数据 → 在数据结构中插入/删除 → 重写整个 docx**。
3. **标题号与表组号是两个独立的编号体系。** 文档中可能存在历史编号缺口（如第10组缺失导致标题号与表组号偏移），绝不假设两者一致。修改后必须逐一校验：标题号 == 表组号。
4. **Word 文本可能跨多个 `<w:t>` 元素。** 绝不能用 `t.text.startswith('14、')` 判断——数字和中文可能在不同 run 中。必须拼接全部 `w:t` 文本后再匹配。
5. **重编号从后往前做。** 前缀替换时从高组号往低组号改，避免 "16→17→18" 的级联覆盖。

### 9.1 触发条件

用户说类似以下表述时触发：
- "把第X组证据写进去"
- "缺第X组，补一下"
- "在X组和Y组之间插入一组"
- "把XX组的证据删掉，后面顺延"

### 9.2 操作流程

```
用户说「插入/删除某组」
  │
  ├─ Step 1：读取现有 docx，提取全量数据结构
  │     ├─ 每组的标题（段落文字）
  │     ├─ 每组的表格（所有行/列的内容）
  │     └─ 组的编号（从第一个数据行提取组号）
  │
  ├─ Step 2：在数据结构中做增删改
  │     ├─ 插入：找到插入位置，插入新组数据
  │     └─ 删除：移除目标组
  │
  ├─ Step 3：在数据结构中统一重编号
  │     ├─ 表内所有组号前缀（如 15-1 → 16-1）
  │     ├─ 页码范围的组前缀（如 15-1~15-16 → 16-1~16-16）
  │     └─ 标题段落号（如 "15、XX工程" → "16、XX工程"）
  │
  ├─ Step 4：用修改后的数据结构重写 docx
  │     └─ 保持原有格式（从原 docx 复制样式和表格模板）
  │
  └─ Step 5：验证
        ├─ 标题号 == 表组号（逐组检查）
        ├─ 无重复组号
        ├─ 页码连续
        └─ 无空白证明目的/无残留模板文字
```

### 9.3 数据结构模板

```python
groups = [
  {
    "title": "1、车道雨棚改建施工工程",
    "group_num": 1,
    "rows": [
      ["1-1", "车道雨棚改建施工合同", "证明原、被告签订……", "1-1~1-13"],
      ["1-2", "验收报告", "证明本工程已经竣工验收……", "1-14"],
      ...
    ]
  },
  ...
]
```

### 9.4 重编号规则

| 场景 | 规则 |
|------|------|
| 在第 N 组后插入新组 | 原有 ≥ N+1 的组号全部 +1，标题号同步 +1 |
| 删除第 N 组 | 原有 ≥ N+1 的组号全部 −1，标题号同步 −1 |
| 仅修改某组内容 | 不触发重编号 |

### 9.5 自检清单（插入/删除专属）

- [ ] 操作前已备份原文件
- [ ] 标题号与表组号逐一校验（每个标题的数字 == 对应表格第一行第一列的组号）
- [ ] 组号无重复、无额外缺口（历史缺口除外，需向用户说明）
- [ ] 插入的新组：证明目的已填写，页码已计算，无模板残留
- [ ] 删除的组：对应的标题段落和空行一并移除
- [ ] 交付前用 `present_files` 打开让用户确认

详细踩坑记录和实现参考见 `references/evidence-list-editing.md`。

## Phase 10：证据编排与打页码（证据清单之后，可选）⚠️ 新增 v2.7.0

证据清单定稿后，立案/举证还需把证据**按清单顺序物理排列**并**每页编页码**（组号-页号）。本环节把 26 组证据合并成单个 PDF，每页打页码。

### 10.0 铁律（踩坑总结，不可违反）

1. **先去重再编排**：重复证据会让页码虚高；去重后必须同步更正证据清单页码。
2. **先摆正再打页码**：扫描件方向（rotation / 横版 / 内容侧躺）必须先归一化。若用 `insert_pdf` 保留 rotation、再按未旋转的 `page.rect` 打页码，页码会跟着页面旋转 90° 跑到侧面——这是"横版扫描件打码错误"的根因。
3. **页码规范**：底部居中、黑色、**16pt（三号）**、格式「组号-页号」。⚠️ 谈字号一律用 pt，中文排版「五号=10.5pt」反而更小，勿混淆。
4. **方向判定以 rotation 标记 + 宽高比为准**，不要依赖 OCR/投影（对中文扫描件和发票不可靠）。转 90° vs 270° 无法纯代码判定，生成预览图让用户确认。

### 10.1 三类方向问题与处理

> 本节针对扫描 PDF 页；**图片类证据（截图/照片文件）的排版走 10.2**，两者共用"方向归一化"判定。

| 情况 | 判定 | 处理 |
|------|------|------|
| rotation ≠ 0 | `page.rotation` 非 0 | `get_pixmap` 自动应用 rotation 摆正 |
| 横版（宽>高） | `rotation==0` 且 `width > height` | 顺时针转 90° 竖过来 |
| 竖版但内容侧躺 | OCR 全乱码（如横版表格被竖扫） | 顺时针转 90° |

### 10.2 图片自动排版（⚠️ 图片类证据默认执行，2026-08-30 新增）

证据里大量是图片（微信聊天记录截图、手机页面截图、照片）。这类证据**不能一图一页硬排**，必须按图片类型自动选排版模式，再逐页打「组号-页号」页码。

**三种排版模式（与帧册 Framebook 排版规则一致）**：

| 模式 | 适用图片类型 | 页面方向 | 布局 | 阅读顺序 |
|------|------------|---------|------|---------|
| **每页 4 张** | 聊天记录截图、手机页面截图等竖长截图（默认） | 竖版 A4 | 2×2 网格 | 左上 → 右上 → 左下 → 右下 |
| **每页 2 张** | 照片类（现场照片、施工照片等） | **横版 A4** | 左右两栏 | 左 → 右 |
| **每页 1 张** | 特别图片：需要看清整页细节的关键凭证、横版大图、表格类截图 | 竖版 A4 | 完整居中 | 单图（较少用，用户指定或明显大图时） |

**模式判定规则**：
1. **默认按证据类型路由**：文件名/来源含"聊天""微信""记录""截图"→ 4 张模式；含"照片""现场"→ 2 张模式；拿不准的组，**列入必问清单随其他问题一并问用户**（见下方必问）
2. 同一组内**模式统一**，不混排（一张 A4 里既有截图又有照片会很乱）；同组确有两种类型图片时，按类型分段各自排版，页码连续
3. **竖版图片在竖版页面放 4 张、横版图片在横版页面放 2 张**——若图片方向与页面方向冲突（如 4 张模式遇横版截图），等比缩放放进格子即可，不旋转图片（旋转会伤害证据可读性）

**排版技术规则（可直接照抄实现）**：
- **等比缩放、完整居中、绝不裁剪、绝不变形**：每张图 `scale = min(格宽/图宽, 格高/图高)`，缩放后在格子内水平垂直居中
- 页边距与间距：4 张模式边距 20pt、格间距 12pt；2 张模式边距 24pt、中缝 18pt；1 张模式边距 24pt
- 页码仍按 Phase 10 铁律打在**底部居中**——注意 4 张模式页脚要预留空间，下边距实际取 `max(20, 页码高度+8)`，避免页码压图
- 每页图片数改动后，**证据清单的页数必须同步重算**：`该组页数 = ceil(图片数 / 每页张数)`，回写清单再编排

**必问（与 8.0 合并一次问完，模板优先级最高）**：① 用户有无自带模板（影响所有排版）② 图片类证据每组按几张一页排？默认建议：聊天截图 4 张、照片 2 张。用户对个别组指定其他模式（如某组关键截图要 1 张一页）时照做。

**自检追加**：
- 每页实际图片数 = 排版模式对应张数（末页可少）、页数 == 清单同步后的预期页数
- 抽查渲染页面：图片无裁剪无变形、阅读顺序正确（4 张模式第一格必须是组内第 1 张图）

### 10.3 输出与自检

- 输出：合并单 PDF（图片转 A4 居中、zip 解压后逐张插入），每页底部居中打「组号-页号」
- self_check：每组实际页数 == 清单预期页数、页码标签数 == 总页数、边界页抽查（1-16 → 2-1）、方向归一化后 rotation 全 0

详细踩坑、重复证据检测、方向归一化代码见 `references/evidence-arrangement.md`。

## Phase 11：证据册 PDF 压缩拆分（法院上传 <100MB 限制）⚠️ 新增 v2.8.0

**目的**：证据册编排打页码完成后，向法院电子诉讼平台提交时单文件通常限 **100MB**。本环节把超限证据册**压缩 + 贪心切页拆分**为编号分册（每份 <100MB），并附拆分说明。核心铁律 4 条：

1. **侦察先行再定参数**：先用 pymupdf 统计图片编码——PNG 占比高（证据册典型，本案 94%）→ 整页渲染重编码收益大（可压到 1/3）；已是 JPEG/JPX 为主则谨慎二次压缩。
2. **200dpi + JPEG q82 是证据册平衡点**：150dpi 与原图分辨率（1240×1754≈150dpi）1:1 最保真但单页 ~209KB；300dpi ~700KB 拆 6-7 份不划算；200dpi 放大 1.33 倍文字/印章/表格线无可见损伤，单页 ~330-420KB。**交付前抽 3 类页面肉眼验证**：照片页、表格页、截图/印章页。
3. **95MB 上限留 5% 余量**：100MB 有十进制（100,000,000）与二进制（104,857,600）两种口径，按 95MB 贪心切页（每页累加、超限封卷，按体积切不按页数等分）同时覆盖两种口径。
4. **🔴 不重新打页码**：原证据册页脚已有「组号-页号」，分册**不得叠加页码**（法院证据讲究原始性）。定位靠每份 PDF 元数据（`subject` 写"原书第X-Y页"）+ 页脚原有页码 + 随附 `拆分说明.txt`。

- 输出：`{案件名}_证据清单+证据册_第{NN}册.pdf`（序号 01 起，排序稳定）+ `拆分说明.txt`（每册原书页码范围/页数/大小/上传顺序）
- 自检：每份字节级 <100MB、分册页数合计 == 原 PDF 页数、元数据含原书页码范围、抽查渲染质量
- 用户还需单份留存时：`--merge` 用 qpdf 合并完整压缩版（不受 100MB 限制）

参数依据、完整代码见 `references/evidence-pdf-split.md`，可复用脚本见 `scripts/split_evidence_pdf.py`。
