# 证据编排与打页码 — 踩坑记录与实现参考

> 2026-08-20 建立，基于「三安建设诉尚正管理」案 26 组证据（949 页）编排打页码的实际操作经验。

证据清单定稿后，立案/举证还需把证据**按清单顺序物理排列**并**每页编页码**（组号-页号）。这一步最容易踩两个坑：**重复证据导致页码虚高**、**扫描件方向没摆正导致页码方向错**。本文记录完整经验与可复用代码。

## 一、重复证据排查（编排前必做）

### 1.1 三类重复

| 类型 | 典型表现 | 案例 |
|------|---------|------|
| **同证据多格式** | 同一张发票既有 `发票.pdf`（2页）又有 `发票.JPG` + `发票(2).JPG`，pdf 就是两张 JPG 的合并版 | 组4 外墙真石漆发票：清单误记"3份4页"，实际 2 份 2 页 |
| **照片 PDF 内部重复页** | 施工照片/工程照片 PDF 里同一张照片被塞了两遍（可能相邻或跨页） | 工程照片 148 页含 6 对重复页，去重后 142 页 |
| **metadata 层面** | 同一 `rel` 路径在 metadata.json 出现多次 | （本案未出现，但需兜底检查） |

### 1.2 检测方法（感知哈希 + 完整像素 MD5 双重验证）

先感知哈希快速筛候选，再完整像素 MD5 精确确认——区分"完全重复"与"连拍相似"（两张连拍照片 aHash 可能撞车但 MD5 必不同）。

```python
import io, hashlib
import fitz
from PIL import Image

def a_hash(img):
    """32×32 灰度均值哈希，快速筛候选。"""
    img = img.convert('L').resize((32, 32), Image.LANCZOS)
    px = list(img.getdata())
    avg = sum(px) / len(px)
    bits = ''.join('1' if p > avg else '0' for p in px)
    return hashlib.md5(bits.encode()).hexdigest()

def md5_page(path, pno, dpi=100):
    """整页像素 MD5，精确确认是否完全相同。"""
    d = fitz.open(path)
    pix = d[pno].get_pixmap(dpi=dpi)
    return hashlib.md5(pix.tobytes('png')).hexdigest()
```

**坑**：遍历图片时扩展名判断必须用 `os.path.splitext(fn)[1].lower()`，用整个文件名 `fn.lower()` 会漏掉全部图片（文件名 ≠ 扩展名）。

### 1.3 去重后的连锁反应

去重会改变组内页数 → **证据清单页码必须同步更正**（不只删文件）。本案去重后 5 组页码变化：组4 20→18、组15 186→180、组18 81→80、组20 111→110、组24 9→8。

## 二、方向归一化（扫描件摆正，打页码前必做）

### 2.1 问题本质（第一性原理）

扫描件的**内容方向**与**页面方向**常不一致：纸横着放进扫描仪、或手机横拍，导致内容侧躺 90°。若合并时原样保留，内容横着，页码也顺着横页面打、方向和位置全错。

### 2.2 三类问题与处理

| 情况 | 判定信号 | 处理 |
|------|---------|------|
| rotation ≠ 0 | `page.rotation` 非 0（90/180/270） | `get_pixmap` 渲染时自动应用 rotation，摆正 |
| 横版（宽>高） | `rotation==0` 且 `rect.width > rect.height`（如发票 4160×3120） | 顺时针转 90° 竖过来 |
| 竖版但内容侧躺 | `rotation==0`、竖版，但 OCR 全是乱码（如横版表格被竖扫） | 顺时针转 90° |

### 2.3 方向判断方法的可靠性（实测结论）

| 方法 | 可靠性 | 说明 |
|------|--------|------|
| tesseract OSD（`--psm 0`） | ❌ 差 | 对中文扫描件、发票（竖排文字/密码区/印章）误判严重 |
| 四方向 OCR 对比 | ❌ 差 | 同一张发票四个方向 OCR 全是乱码，无法区分 90° vs 270° |
| 投影法（水平/垂直投影方差） | ❌ 误报多 | 合同里的横版表格、横向照片被误判为"侧躺"，扩大打击面 |
| **rotation 标记 + 宽高比** | ✅ 可靠 | 这是最可靠的信号，作为主要判定依据 |

**结论**：方向判定以 `rotation` 标记 + 宽高比为主，不要依赖 OCR/投影。转 90°（顺）还是 270°（逆）**无法纯代码判定**（结果差 180°），生成预览图让用户确认。

### 2.4 核心实现

```python
def add_pdf_page(out, src_doc, page_idx):
    """单个 PDF 页：方向归一化后插入 A4。"""
    pg = src_doc[page_idx]
    rot, w, h = pg.rotation, pg.rect.width, pg.rect.height
    need_raster = (rot != 0) or (w > h)          # 需摆正
    if need_raster:
        pix = pg.get_pixmap(dpi=180)             # 应用 rotation
        img = Image.open(io.BytesIO(pix.tobytes('png')))
        if w > h:
            img = img.rotate(-90, expand=True)   # 顺时针 90°
        # 等比缩放居中插入 A4（rotation=0 新页）
        ...
    else:
        new_page = out.new_page(width=w, height=h)
        new_page.show_pdf_page(new_page.rect, src_doc, page_idx)
```

**铁律**：打页码必须发生在"方向归一化之后"的新页上。若用 `insert_pdf` 保留 rotation、再按 `page.rect`（未旋转坐标系）打页码，页码会跟着页面旋转 90°，跑到侧面——这是"横版扫描件打码错误"的根因。

## 三、页码规范（用户选定，沿用）

- **格式**：`组号-页号`（如 1-1、1-16、26-48），每组独立从 1 起，组间互不影响
- **位置**：底部居中
- **颜色**：黑色
- **字号**：**16pt（三号）**。踩坑记录：曾按"五号=10.5pt"理解反而更小，用户最终确认要 16pt（三号）；⚠️ 中文排版号数越大字越小，谈字号一律用 pt 对齐
- 页码文本是纯数字+连字符，用默认 `helv` 字体即可（不涉及中文）

---

## 四、页数核对口径（补充自检）

1. **zip 内图片数 ≠ 清单页数**：如"施工照片.zip"清单写 7 页，实际解压只有 6 张（之前 MinerU 把 zip 的 7 个条目含目录当 7 页）。以实际图片数为准。
2. **照片 PDF 去重后页数变化**：去重删页会改变组内页数，编排脚本须用去重后的实际页数重新累计页码，并与证据清单同步更正。
3. **单页扫描件页数**：jpg/png 每张 = 1 页；PDF 用 `fitz.page_count`。

## 五、时间信息补充（证据清单"证明事实"缺时间时）

证据清单里某些组的"证明事实"只有金额、没有时间（如只有"合同金额 X、已支付 X"）。应从证据文件里找时间补入：

| 证据项 | 找时间的位置 |
|--------|------------|
| 结算申请表 | "已于 YYYY 年按合同约定完成" |
| 工程结算单/报价单 | "日期：YYYY 年 M 月—YYYY 年 M 月"（施工期间） |
| 请款通知书 | 落款日期 |
| 项目验收表 | "验收日期"（常只有年份，月日空白则如实写"YYYY 年"，不编造） |
| 施工照片 | 照片水印时间 |

**原则**：只写文件里真实提取到的时间，月日空白时精确到"年"，绝不编造具体日期。

## 六、图片自动排版（截图每页4张 / 照片每页2张 / 特别图每页1张）

> 2026-08-30 新增（v2.10.0），排版规则与帧册 Framebook（`~/Downloads/toolkit-packages_chat-recording-evidence/assets/app.js` 的 `pdfPageSize` / `pdfPlacement` / `fitImage`）保持一致。

### 6.1 模式与页面参数

| 模式 | 适用 | 页面（pt，PDF 单位） | 布局参数 |
|------|------|--------------------|---------|
| 每页 1 张 | 关键凭证/横版大图（少用） | 竖版 595.276 × 841.89 | 边距 24，完整居中 |
| 每页 2 张 | 照片类 | **横版 841.89 × 595.276** | 边距 24，中缝 18，左右两格 |
| 每页 4 张 | 聊天记录/手机截图（默认） | 竖版 595.276 × 841.89 | 边距 20，格间距 12，2×2 四格 |

### 6.2 核心代码（pymupdf 实现，可直接复用）

```python
import fitz

PAGE = {"1": (595.276, 841.89), "2": (841.89, 595.276), "4": (595.276, 841.89)}

def cells(per_page):
    """返回每页各格子的 (x, y, w, h)，坐标原点左上，y 向下——阅读顺序已编码在格子顺序里。"""
    pw, ph = PAGE[str(per_page)]
    if per_page == 1:
        m = 24
        return [(m, m, pw - 2*m, ph - 2*m)]
    if per_page == 2:
        m, gap = 24, 18
        cw = (pw - 2*m - gap) / 2
        return [(m, m, cw, ph - 2*m), (m + cw + gap, m, cw, ph - 2*m)]
    m, gap = 20, 12
    cw = (pw - 2*m - gap) / 2
    ch = (ph - 2*m - gap) / 2
    # 左上 → 右上 → 左下 → 右下（fitz 的 y 轴向下，直接按行序排列即读序）
    return [(m, m, cw, ch), (m + cw + gap, m, cw, ch),
            (m, m + ch + gap, cw, ch), (m + cw + gap, m + ch + gap, cw, ch)]

def place_image(img_w, img_h, cell, bottom_reserve=0):
    """等比缩放居中进格子；bottom_reserve 为页码预留高度（自下而上收缩格子）。"""
    x, y, cw, ch = cell
    ch -= bottom_reserve
    scale = min(cw / img_w, ch / img_h)
    w, h = img_w * scale, img_h * scale
    return x + (cw - w) / 2, y + (ch - h) / 2, w, h   # 居中偏移
```

**坑与铁律**：
- **等比缩放、完整居中，绝不裁剪绝不变形**——证据图裁剪 = 变造证据。`scale = min(两方向比值)`，不许用 `max`
- 4 张模式的格子高度要**为页脚页码让位**：`bottom_reserve ≈ 页码字号 + 8pt`（16pt 页码 → 预留 ~28pt），否则第四行页码压图
- 阅读顺序由**格子顺序**保证：图片按组内顺序逐个放入 `cells()` 列表顺序的格子，第 5 张起新页——天然实现"左上→右下"
- 插图用 `page.insert_image(rect, filename=...)`，rect 用 `fitz.Rect(x, y_top, x+w, y_top+h)`；fitz 坐标原点在**左上**，与上面 cells() 一致，不要混用 PDF 原生底左原点
- 模式判定走文件名关键词（"聊天/微信/记录/截图"→4 张，"照片/现场"→2 张），拿不准的列入必问清单问用户；同组模式统一，混类型分段各自排版页码连续
- 每页张数定稿后**回写证据清单页数**：`组页数 = ceil(图片数 / 每页张数)`，再进打页码流程

### 6.3 自检追加（编排脚本内置）

- [ ] 每页实际图片数 == 模式张数（末页可少）
- [ ] 组页数 == 证据清单同步后的预期页数
- [ ] 抽查渲染：图片无裁剪无变形、4 张模式首格是组内第 1 张图
- [ ] 页码未被图片遮挡（末行图底边距 ≥ 页码区高度）

## 七、编排脚本自检（不可跳过）

生成编排 PDF 前，脚本必须内置 self_check：
1. 每组实际页数 == 证据清单预期页数（差一页都不能交付，逐组排查）
2. 页码标签数 == 输出总页数
3. 边界页抽查（每组末页 = 下一组首页前一位，如 1-16 → 2-1）
4. 方向归一化后 rotation 应全为 0
