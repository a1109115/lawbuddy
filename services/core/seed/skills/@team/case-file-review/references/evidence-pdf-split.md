# 大证据册 PDF 压缩拆分（法院系统 <100MB 限制）— 踩坑记录与实现参考

> 2026-08-20 建立，基于「三安建设诉尚正管理」案证据册（961 页 / 1.2GB）拆分为 4 份 <100MB 分册的实际操作经验。

证据册编排打页码完成后，向法院（人民法院诉讼资源网 / 各地电子诉讼平台）提交时普遍遇到**单文件 <100MB 上传限制**。本案 961 页 1.2GB 无法直接上传，需要压缩 + 拆分 + 编号。本文记录完整经验与可复用代码（`scripts/split_evidence_pdf.py`）。

---

## 一、触发场景与决策路径

| 场景 | 处理 |
|------|------|
| 证据册 >100MB 且需上传法院 | **压缩 + 贪心切页拆分**（本方案） |
| 拆分后仍需单份留存/打印/归档 | `qpdf --empty --pages 分册... -- 完整版.pdf` 合并（不受 100MB 限制） |
| PDF 本身 <100MB 但想瘦身 | 直接走压缩，不拆分 |
| 含 OCR 文本层 / 矢量元素的 PDF | 整页渲染会丢文本层；先用 `page.get_text()` 确认——证据册几乎全图，无文本层需求 |

**决策原则**：先侦察（页数、图片编码、每页大小分布）再定参数，不拍脑袋。压缩目标不是"尽量小"，而是"法院看得清的最小体积"。

---

## 二、侦察先行（分析图片构成，决定压缩空间）

```python
import fitz, collections
doc = fitz.open(src)
print("pages:", doc.page_count)
enc = collections.Counter(); total_bytes = 0; n = 0
for pno in range(doc.page_count):
    for im in doc[pno].get_images(full=True):
        info = doc.extract_image(im[0]); enc[info["ext"]] += 1
        total_bytes += len(info["image"]); n += 1
print(enc, f"{total_bytes/1e6:.0f}MB / {n}张")
```

**判读**（本案实测 961 页 1.2GB）：
- `png: 10726`（94%）→ **压缩空间巨大**。PNG 是无损编码，扫描/截图证据转 JPEG 视觉无差异、体积骤降
- `jpeg/jpx` 为主 → 已压缩，收益有限（二次压缩有损，谨慎）
- 大量 128×40 之类小图标 PNG → 体积小，可忽略，随整页渲染统一转 JPEG
- 页面主图 1240×1754 ≈ **150dpi A4**、1489×2105 ≈ **180dpi A4** → 渲染 dpi 以此为基准选择

**结论**：PNG 占比高 → 整页渲染重编码，体积可压到 1/3~1/4。

## 三、压缩参数（实测对比后选定）

| DPI × 质量 | 单页大小（A4） | 结论 |
|-----------|--------------|------|
| 150dpi q80 | ~209KB | 与原图分辨率（1240×1754≈150dpi）1:1，最保真 |
| **200dpi q82（选定）** | **~330-420KB** | 放大 1.33 倍但文字、印章、表格线无可见损伤；安全余量最大 |
| 300dpi q85 | ~628-785KB | 体积偏大，拆 6-7 份，不划算 |

- **整页渲染**：`page.get_pixmap(matrix=fitz.Matrix(DPI/72, DPI/72), colorspace=fitz.csRGB, alpha=False)` + `pix.tobytes("jpeg", jpg_quality=q)`
- **为什么不用 `doc.replace_image()`（PNG→JPEG 换编码保分辨率）**：也可行，但 1 万+ 张图逐个处理慢、且小图转 JPEG 可能反而变大；整页渲染统一编码、体积可预测、实现最简单。前提是确认页面几乎全图（证据册成立）
- **为什么不用 ghostscript**：`-dPDFSETTINGS=/ebook`（150dpi）偏糊、`/printer`（300dpi）偏大，粒度粗；1.2GB 处理慢
- **为什么不用"直接拆页不压缩"**：1.2GB/100MB ≈ 13 份，上传 13 次体验差；压缩后 4 份
- **q82 的理由**：q80 vs q85 单页差 ~10%，视觉无差异；印章红、黄色高亮在 q82 下无可见伪影

**质量验证铁律**：抽 3 类代表性页面渲染查看——照片页（验收/现场）、表格页（清单/明细）、截图页（聊天记录）+ 印章页。肉眼确认后才交付。

## 四、拆分算法（贪心切页 + 安全余量）

```python
LIMIT = 95_000_000   # 每份上限字节。⚠️ 100MB 有两种口径（100,000,000 或 104,857,600），留 5% 余量同时覆盖
for pno in range(total):
    jpg = render(page)
    if part_buf and part_size + len(jpg) > LIMIT:
        flush()          # 封卷另开新 PDF
    part_buf.append((pno, jpg)); part_size += len(jpg)
```

- **贪心切页**（每页累加、超限封卷），不是等分页数：页大小不均（照片页大、文字页小），按体积切保证每份都贴上限、份数最少
- 每页独立判断 `part_size + len(jpg) > LIMIT` 再封卷，保证**任何单份 <LIMIT**
- 输出页尺寸：`doc.new_page(width=page.rect.width, height=page.rect.height)`，保留横向页（长截图切图页等）

## 五、命名、元数据与"不改内容"铁律

- **命名**：`{案件名}_证据清单+证据册_第{NN}册.pdf`，序号 `01/02/...` 保证排序稳定
- **元数据**：每份 `doc.set_metadata({"title": ..., "subject": f"原书第{p0}-{p1}页，共{TOTAL}页"})`——法官/律师打开 PDF 属性即可定位原书页码范围
- **🔴 不重新打页码（铁律）**：证据册每页页脚已有「组号-页号」（编排环节打的），**分册不得叠加页码文字**——法院证据讲究原始性，篡改呈现（哪怕加页码）可能被质疑。定位靠元数据 + 页脚原有页码
- 附一份 `拆分说明.txt`：每册原书页码范围、页数、大小、上传顺序，随目录交付

## 六、验证与自检（差一项都不交付）

```bash
# 1. 每份 <100MB（字节级校验，不用 ls -lh 的取整）
pdfinfo "第XX册.pdf" | grep Pages
# 2. 总页数 = 原 PDF 页数（961 → 222+253+258+228 = 961）
# 3. 元数据抽查：Title/Subject 含原书页码
# 4. 质量抽查：每份抽 首页/中页/末页 渲染查看（照片/表格/印章/截图）
```

**实测数据**（本案，961 页 1.2GB，200dpi q82，95MB 上限）：
- 第01册 原书 1-222（222页 95.0MB）｜第02册 223-475（253页 94.5MB）｜第03册 476-733（258页 95.0MB）｜第04册 734-961（228页 83.4MB）
- 总输出 368MB（原 28%），4 份，耗时 1 分 51 秒（pymupdf 整页渲染）

## 七、可复用脚本

`scripts/split_evidence_pdf.py` —— 参数化版本（`--src --outdir --limit-mb --dpi --quality [--merge]`）：
- 默认拆分；`--merge` 额外用 qpdf 合并一份完整压缩版（供留存/打印/归档）
- 生成 `拆分说明.txt`（每册页码范围 + 上传说明）
- 内置页数/大小自检输出，不通过不结束

**依赖**：`pymupdf`（渲染/切分）、`qpdf`（合并完整版，仅 --merge 时需要）、`pdfinfo`（poppler，自检用）。
