## 1. 改造背景与目标

### 1.1 已确认的问题

1. **自主能力与交付稳定性不匹配**
   - WFA-LAW-001 自主 Agent 用 73 轮取得 branch 98.3、merge 76.5，官方判定完全通过。
   - WFA-LAW-013 自主 Agent 跑满 900 轮，未生成完整 `answers.json`，官方得分 0。
   - 说明瓶颈是任务收束与交付保障，不是单纯模型能力或轮数不足。

2. **预算与恢复语义不统一**
   - `agent/budget.py` 支持五类预算和持久化计数；自主循环主要使用独立的 `MAX_ROUNDS`、`MAX_TOOL_CALLS`。
   - 自主循环的轮次、工具计数在恢复时未完整续接，存在续跑后重新获得预算的风险。
   - `agent.start` 已接收 `budget`，但自主运行链路的墙钟、模型调用、Token 预算没有统一生效。

3. **交付契约只描述文件，未描述工作全集**
   - 当前契约能创建 CSV/JSON 骨架，但不能表达“20 份协议 × 15 个问题 = 300 个必须进入终态的单元格”。
   - 收尾检查只判断文件存在、可解析、非空，未校验行全集、合法值、证据状态、派生一致性。
   - `expectedEntities` 等 Python 已读取字段未完整进入共享 Schema 与规范化结果。

4. **工作、阅读和证据状态不足以支撑大卷宗**
   - 阅读账本上限 600 条、证据账本上限 240 条；WFA-LAW-001 约 1,865 页，WFA-LAW-013 有 300 个答案格。
   - 固定容量字典会淘汰早期工作状态，不能作为大任务的最终完成依据。

5. **检索作用域与覆盖存在确定性缺口**
   - 查询缓存键未完整包含 `documentIds`、文档版本等范围信息，同词不同范围可能复用错误结果。
   - 全局 Top-N 已满时，不再为未覆盖文档补席位，多文档任务可能出现整份材料零覆盖。

6. **上下文与故障恢复仍以整段对话为中心**
   - 历史压缩只保留截断摘要，不能保证未提交单元格、精确选项、引文和失败原因完整保留。
   - 子代理主要负责检索，不具备按工作单元执行、暂存、恢复和幂等提交能力。
   - 并行调用发生断连时，仍可能形成空批次或重复副作用。

7. **运行状态与真实交付状态可能不一致**
   - 强制终答后计划步骤可能被统一标记为 done。
   - `COMPLETED_WITH_WARNINGS` 同时承载“引用待核实”和“交付未完成”，用户无法直接区分。

### 1.2 核心改造方向

> 模型负责检索、阅读和判断；Harness 负责任务分解、状态持久化、预算调度、故障恢复、结构交付和完成验收。

目标架构为：

```text
用户任务
  → 任务契约编译器
  → 工作全集与依赖图
  → 运行控制器（预算 / 调度 / 恢复 / 并发）
  → 主 Agent + 工作型子代理
  → 持久化工作账本 + 证据库 + 暂存结果
  → 确定性物化 / 聚合 / 校验
  → submission/ 正式交付物
```

不得恢复为固定六节点阅卷流程。工作单元由任务契约和材料规模动态生成，模型在每个工作单元内保持自主决策。

### 1.3 可量化目标

以下指标分为**上线硬门槛**和**优化目标**。硬门槛未满足不得全量上线；优化目标未满足不触发自动回滚，但必须形成下一迭代缺陷单。

| 指标 | 当前基线 | 上线硬门槛 | 优化目标 |
| --- | --- | --- | --- |
| 结构交付率 | 自主 013 缺少完整派生文件 | 所有测试任务契约声明的主交付物及派生/配套交付物均存在且可解析，100% | 同左 |
| 工作全集覆盖 | 无系统化记录 | 必需行/实体覆盖率 100%；未确认值留空并单独记状态 | 同左 |
| 工作单元终态率 | 无工作单元模型 | committed / needs_human / blocked 合计 100%，无从未尝试项 | 同左 |
| 预算恢复正确性 | 主预算可能重置 | 取消、失败、进程重启后续跑，预算重置次数 0，重复提交次数 0 | 同左 |
| 检索范围正确性 | 缓存缺少范围键 | 同词不同 `documentIds` 串用结果 0 次；跨案召回 0 次 | 同左 |
| 大账本完整性 | 600 页 / 240 证据上限 | 1,865 页、300 格以上无状态淘汰 | 同左 |
| 网络故障交付 | 断连可产生空批次 | 注入断连后静默空批次 0 个，重复副作用 0 次 | 同左 |
| 代表任务 001 | 自主综合 87.4 | 同模型同版本连跑 3 次，综合分中位数 ≥82.4 | 中位数 ≥87.4 |
| 代表任务 019 | 自主综合 83.1 | 同模型同版本连跑 3 次，综合分中位数 ≥78.1 | 中位数 ≥83.1 |
| 代表任务 013 | 自主综合 0 | 3 次均有完整交付且综合分均 >0 | 中位数 ≥8.2 |
| 既有 22 题定向链路 | 平均 31.6 | 全量复测平均 ≥29.6，且结构交付 22/22 | 平均 ≥31.6 |
| 上下文效率 | 001 约 505 万输入 Token | 记录每提交格 Token，禁止统计缺失 | 001/019 每提交格输入 Token 较各自 V1 基线下降 ≥20%；013 建立新基线 |
| 重复工作 | 有重复读取/检索计数 | 重复读取率、重复检索率必须可查询 | 每百次工具调用的重复读取与重复检索次数下降 ≥30% |

指标口径补充：

1. **结构交付率**只统计声明了文件交付物的任务，计算式为“主、派生文件均存在且可解析的任务数 ÷ 应交付文件的任务数”。纯问答任务不进入分母，但必须有终答并完成引用守门。
2. **工作全集覆盖率**按契约声明的必需行或实体计算；空答案格只要已登记 `needs_human` 或 `blocked` 状态，也计入结构覆盖，但不得计为已确认答案。
3. **每提交格 Token**只统计进入 `committed` 状态的单元格；V1 没有提交格的任务不计算降幅，只建立新基线。
4. 评测中的“禁止真值路径访问”约束 Agent 及其工具运行期；评分阶段只允许官方 `scorer` 读取 `reference/`。

## 2. 改造边界与不变量

### 2.1 必须保持的业务底线

1. 原件只读；子代理只能写暂存区，正式交付物只能由交付控制器原子写入。
2. 所有事实性答案必须保留文档 ID、版本 ID、页码和原文短引；无可靠来源必须标为 `needs_human`。
3. 未确认答案不得写成确定事实；不得把 `needs_human` 当作普通合法选项写入 `answer`。
4. 派生结果只能由已提交数据计算；未确认单元格不得按否定值参与统计。
5. 日志、审计 metadata、事件 payload 只记录 ID、数量、状态、错误码，不记录案件原文、完整引文、密钥或个人信息。
6. 新表只存于应用加密数据库；原文短引不得进入普通文本日志。
7. 新增 IPC 字段必须同步修改 `packages/contracts`、Core、preload、主进程与渲染层，不允许前端自建平行类型。
8. 评测只能读取任务输入；禁止读取官方 `reference/`、真值、评分器内部答案或评测专用隐藏路径。

### 2.2 非目标

1. 不通过更换更强模型提高分数。
2. 不新增向量数据库作为本次前置依赖；先修复检索范围、覆盖和缓存正确性。
3. 不重写 Electron UI，不改变既有布局与交互入口。
4. 不一次性删除旧 Loop/Graph；先统一公共状态与预算，再逐步收敛。
5. 不为 WorkflowArena 单独增加任务答案规则；所有能力必须对通用法律任务生效。

## 3. 总体实施步骤

## 阶段 A：准备阶段

### A-01 冻结可复现基线

**责任角色：QA 组**

执行事项：

1. 记录当前 commit SHA、工作区 diff、模型 ID、模型服务商、运行参数、数据库最大迁移版本。
2. 归档 2026-11-12 的 22 题结果、001/013/019 自主运行日志、交付物、评分 JSON 和效率统计。
3. 建立 `services/core/evals/reports/harness/baseline/`，保存以下清单：
   - `manifest.json`：代码、模型、数据快照哈希、迁移版本；
   - `batch-22-summary.json`：22 题批量结果；
   - `e2e-001.json`、`e2e-013.json`、`e2e-019.json`：代表任务结果；
   - `metrics.json`：轮次、工具调用、Token、重复读取、重复检索、交付状态。
4. 基线目录只读保存，后续报告不得覆盖。

**交付物**：基线清单、日志归档、评分归档、指标归档。

**通过条件**：同一基线可由另一名 QA 按清单定位到代码、输入、输出和评分器，四项缺一不可。

### A-02 备份与恢复演练

**责任角色：发布组**

执行事项：

1. 关闭应用及 Core 子进程，备份当前工作空间目录、profile 数据目录和密钥环引用信息。
2. 记录 `schema_migrations` 最大版本、数据库文件大小和 SHA-256。
3. 在隔离目录恢复备份，启动应用并验证：
   - 案件列表可打开；
   - 文档页可读取；
   - 历史任务与产物可查看；
   - API Key 只显示 `configured`，不显示明文。
4. 恢复演练不得修改原工作空间。

**交付物**：备份包、备份哈希清单、隔离恢复记录。

**通过条件**：隔离恢复全部成功；任一项失败则停止升级，先修备份流程。

### A-03 冻结契约与迁移设计

**责任角色：Core-Agent 组、前端组、QA 组**

执行事项：

1. 评审本方案第 4 节的 V50 表结构和共享 Schema。
2. 为每个新增字段标明：来源、写入方、读取方、是否含敏感内容、是否进事件、是否进日志。
3. 确定运行时版本钉住规则：任务创建时记录 `runtimeVersion`，恢复时不得跨 V1/V2。
4. 确定旧任务迁移策略：旧任务标记 `legacy`，不从旧 messages 猜测工作单元，不回填事实答案。
5. 形成接口差异清单，覆盖 Core、contracts、preload、主进程、Renderer。

**交付物**：V50 SQL 草案、Schema 差异表、运行时兼容矩阵、事件字段清单。

**通过条件**：所有新增字段均有唯一写入方和读取方；敏感字段均有存储与日志边界。

### A-04 建立验收测试矩阵

**责任角色：QA 组**

执行事项：

1. 将第 6 节验收项逐项映射到自动化测试或明确的手工步骤。
2. 准备以下 fixture：
   - 20 文档 × 15 问题的 300 格合同任务；
   - 13 被告刑事任务；
   - 超过 600 页、超过 240 条证据的大账本任务；
   - 同词不同 `documentIds` 的检索任务；
   - 可注入 429、超时、首字前断连、正文断连、工具参数断连的模型网关。
3. 固化 30% / 60% / 90% 中断注入点。
4. 规定所有性能对比必须使用同一 commit、同一模型、同一输入快照。

**交付物**：验收矩阵、fixture、故障注入配置、结果模板。

**通过条件**：每个上线硬门槛都有唯一测试编号、执行命令、预期结果和证据保存路径。

### 阶段 A 出口条件

A-01 至 A-04 全部通过；未完成备份恢复演练或验收矩阵，不得进入开发阶段。

## 阶段 B：开发改造阶段

### B-01 任务契约与工作账本

**责任角色：Core-Agent 组**

执行任务：

1. 新增 V50 迁移，创建第 4.1 节规定的表和索引。
2. 新增 `agent/work_contract.py`：
   - 扩展交付契约；
   - 编译工作全集、依赖图、合法值与验收规则；
   - 仅从用户输入和材料元数据生成结构，不生成法律结论。
3. 新增 `agent/work_ledger.py`：
   - 提供工作单元、答案格、证据、交付物的读写接口；
   - 所有状态迁移使用数据库事务；
   - 按 `task_id + work_unit_id` 幂等提交。
4. 修正 `deliverables.normalize_specs`，保留并校验 `expectedEntities`、`questions`、`multiPoints`、`derivedArtifacts` 等字段。
5. 更新 `packages/contracts/src/index.ts`，保持双端字段一致。

**交付物**：V50、契约编译器、工作账本、共享类型、迁移单测。

**出口测试**：

- 20 × 15 任务生成 300 个唯一工作单元；
- 重复编译不产生重复单元；
- 300 格与 1,865 页状态无淘汰；
- `expectedEntities` 规范化前后完全一致；
- 旧库升级后旧任务仍可读取。

### B-02 统一预算、检查点与检索正确性

**责任角色：Core-Agent 组、检索组**

执行任务：

1. 以 `agent/budget.py` 为唯一预算实现，自主循环每轮调用统一记账接口。
2. `runner.py` 将任务预算注入自主状态；墙钟、模型调用、工具调用、Token、子代理轮次统一生效。
3. 检查点恢复完整计数：主轮次、工具调用、模型调用、Token、子代理轮次、已用墙钟、效率计数。
4. 运行时版本随任务钉住；V1 任务按 V1 恢复，V2 任务按 V2 恢复。
5. 检索缓存键改为：案件范围、文档 ID 集、文档版本、查询词、limit、索引版本。
6. 多文档检索按“文档全集 → 文档内页级检索”执行；全局 Top-N 只作为补充。
7. 缓存和阅读记录按文档版本失效，禁止旧版本结果显示为已支持。

**交付物**：统一预算层、恢复实现、检索缓存与覆盖改造、专项测试。

**出口测试**：

- 低预算运行 → 取消 → 恢复，累计计数连续；
- 同词全库检索后限定 A 文档，再限定 B 文档，结果范围各自正确；
- 20 文档任务每个必需文档均有检索终态；
- 文档换版后旧缓存和旧证据状态失效。

### B-03 动态调度与确定性交付

**责任角色：Core-Agent 组**

执行任务：

1. 新增 `agent/scheduler.py`：
   - 按依赖、优先级、失败次数选择工作单元；
   - 支持文档 × 问题组、被告 × 字段组两类动态分片；
   - 每个工作单元记录尝试次数、成本、输出和终态。
2. 将预算拆为探索预算与交付保留预算；交付保留预算不得被检索或子代理占用。
3. 单个工作单元因检索无命中、解析失败或证据不足连续两次无有效结果后标记 `needs_human`；模型服务或网络故障标记 `blocked`，不得误标为证据不足。两类状态都必须继续调度其他单元，不得单点耗尽全任务预算。
4. 新增 `agent/delivery_controller.py`：
   - 接收结构化候选并写暂存区；
   - 按契约补齐完整行全集；
   - 原子生成正式 CSV/JSON；
   - 自动执行已声明的派生聚合；
   - 写后重新读取并校验。
5. 将完成状态拆为 `runStatus` 与 `deliveryStatus`；交付不完整不得将所有计划步骤标记 done。
6. 产物每次原子提交后立即登记，不只依赖任务结束时的统一扫描。

**交付物**：调度器、交付控制器、派生聚合、交付状态机、产物即时登记。

**出口测试**：

- 任意中断点文件均可解析，行全集覆盖 100%；
- 只有 60% 答案确认时，也能生成结构完整的部分交付物；
- 派生文件与当前主表一致；
- 未确认格不按否定值参与聚合；
- 单工作单元连续失败不会阻塞其他单元；
- 交付不完整时 UI 不显示全部完成。

### B-04 上下文、工作型子代理与故障恢复

**责任角色：Core-Agent 组**

执行任务：

1. 新增 `agent/context_builder.py`：
   - 稳定规则作为固定前缀；
   - 动态任务状态单独组装；
   - 按当前工作单元注入相关证据和缺口；
   - 未提交单元格、合法选项、引文、失败原因不得依赖截断摘要保存。
2. 新增工作型子代理执行器：
   - 每个子代理绑定明确工作单元；
   - 使用独立上下文；
   - 只写暂存区；
   - 子任务状态、检查点、尝试次数持久化；
   - 主 Agent 负责冲突处理和必要复核。
3. 增加统一并发控制与熔断：
   - 初始最多 2 个模型工作流；
   - 429、连续断连、超时自动降并发；
   - 恢复后按工作单元重试，不重放已提交副作用。
4. 所有写操作携带 `taskId + workUnitId + attempt` 幂等键。

## 6. 最终验收条件

只有同时满足以下条件，才允许全量切换：

1. 阶段 A 至阶段 D-03 的任务和交付物全部完成。
2. 静态检查、现有回归、迁移、15 项专项测试全部通过。
3. 001/013/019 三次复测达到第 1.3 节硬门槛。
4. 22 题定向链路平均 ≥29.6；V2 自主链路结构交付 22/22。
5. 任意 30% / 60% / 90% 中断均有可解析交付物，无重复提交。
6. 预算恢复、检索范围、跨案、版本失效、敏感信息检查全部通过。
7. 灰度 20 + 50 个任务无严重故障。
8. 回滚演练成功，回滚后旧任务、文档、产物、密钥配置可用。
9. 发布组、Core-Agent 组、前端组、QA 组均在验收记录中签字确认；任何一方有未关闭的硬门槛失败项，不得切换。

## 7. 回滚机制

### 7.1 回滚触发条件

| 级别 | 触发条件 | 立即动作 |
| --- | --- | --- |
| S0 | 数据丢失、跨案召回、密钥或敏感原文泄漏、原件被修改 | 停止全部 V2 任务，禁用 V2，保留证据并回滚 |
| S1 | 结构交付率 <100%、预算恢复重置、重复提交、跨运行时恢复、交付状态伪造完成 | 停止新建 V2 任务，切回 V1，运行中的 V2 任务进入安全收尾 |
| S2 | 代表任务硬门槛失败、22 题定向平均分 <29.6、迁移或恢复测试失败 | 禁止扩大灰度，退回上一稳定候选版本 |
| S3 | 性能目标未达、非阻断 UI 展示异常、单项效率退化 | 不自动回滚；登记缺陷并限制相关新能力 |

任何 S0/S1 触发后，不得以“再观察一段时间”为由继续扩大灰度。

### 7.2 回滚前准备

1. 记录当前 commit、安装包版本、数据库版本、运行时开关、在跑任务清单。
2. 导出 V2 已生成的交付物和 Harness 报告；不得删除 V50 新表。
3. 对在跑任务逐项记录 `taskId`、`runtimeVersion`、最后检查点、交付状态。
4. 停止新建 V2 任务；运行中任务只允许执行暂存提交和交付物化，不再发起新检索。

### 7.3 应用配置回滚

1. 将新任务默认运行时切回 `legacy`。
2. 已存在的 V2 任务保持原版本钉住，禁止用 V1 直接恢复。
3. 对未完成的 V2 任务提供两种处理：
   - 保留 V2 兼容包完成安全收尾；
   - 取消任务并保留只读交付物，由用户确认后新建 V1 任务。
4. 验证新建任务使用 V1，旧 V1 任务可恢复。

### 7.4 代码与安装包回滚

1. 停止应用与 Core 子进程。
2. 安装上一份通过验收的候选包，不执行破坏性 Git 操作。
3. 保留 V50 新表；旧版本只读取既有表，不执行 down migration。
4. 若旧版本因新表无法启动，先修复兼容读取；不得直接删除新表或历史任务。
5. 启动后检查案件、文档、任务、产物、模型配置状态。

### 7.5 数据库恢复

仅在以下情况使用备份还原：迁移事务外工具造成损坏、数据库无法打开、人工误操作导致数据不一致。

操作顺序：

1. 停止应用与 Core。
2. 将当前损坏库改名保留，不覆盖删除。
3. 用阶段 A 的备份恢复工作空间与 profile 数据目录。
4. 核对备份哈希和密钥环归属。
5. 启动隔离实例验证后再替换正式目录。
6. 记录恢复点之后可能丢失的新任务，并单独导出可保留的交付物。

### 7.6 回滚后验证

必须完成：

- 应用与 Core 可启动；
- 案件和文档可读取；
- 旧任务可恢复；
- 已交付文件可打开；
- 新任务使用 V1；
- 无跨案、无密钥异常、无新增数据丢失；
- `schema_migrations` 与恢复策略一致；
- 形成回滚原因、影响范围、数据处理和重新进入条件记录。

### 7.7 重新启用 V2 的条件

1. 回滚根因已定位到具体代码和测试。
2. 失败场景已加入自动化回归。
3. 相关硬门槛重新全部通过。
4. 重新完成一次代表任务三次复测和小范围灰度。
5. 重新生成备份与回滚演练记录。

## 9. 完成定义

本方案不以“代码已合并”作为完成标准。只有以下四项同时成立，才能宣布改造完成：

1. 所有硬门槛通过，证据完整；
2. V2 已全量切换，旧任务可恢复；
3. 回滚路径经过实际演练，不是文档假设；
4. 新基线已归档，后续每次改动可用同一指标比较。

最终形成的稳定能力是：**模型可以自主探索，但系统始终知道做什么、做到哪、剩什么、如何恢复，以及怎样把已有结果可靠交付。**
