# LawBuddy·文书生成模式升级改造方案

> 文档性质：产品与技术分析、升级改造记录  
> 分析日期：2026-11-02  
> 实施状态：阶段一至阶段四已按本文落地，自动化验收见 §11.2（`m3_docgen` G15–G26 全绿 + 前端 49 项测试）。  
> 目标：将文书生成从“模板字段与起草信息驱动”升级为“关联案件上下文驱动、对话式生成与迭代、关键决策主动询问”的连续工作流。

---

## 1. 升级背景与核心判断

当前项目已经具备文书生成所需的多项底层能力：关联案件只读共享、模板与槽位、案件原文引证校验、缺失信息占位、Word 草稿落盘、AI 修订、版本比较与恢复、定稿与导出门禁。此次升级不应推倒重建，而应调整任务编排和主交互，把这些能力串成更自然的对话流程。

目标体验可以概括为：

1. 用户在文书任务中已关联案件，只需选择文书模板并发送任务。
2. AI 先主动了解关联案件的案件信息、材料、记忆和已有分析，不再要求用户重复填写基本案件信息。
3. 能从案件原文确认的信息自动带入并保留来源；无法确认的普通缺失信息使用 `xx`，不因此阻塞草稿。
4. 只有立场、请求、辩护或代理策略等会实质改变文书方向的决策，才暂停并向用户提问。
5. 生成后，用户继续通过自然语言修改，AI 基于当前稿迭代新版本；预览、差异、恢复和导出围绕同一会话展开。
6. 用户上传自己的 `.docx` 文件即可新增自定义模板，不要求先手工改写成 Markdown 或逐项配置字段。

### 1.1 本次升级解决的主要问题

| 当前体验 | 目标体验 |
| --- | --- |
| 模板选择会回填一段带蓝色待填片段的提示词，用户仍感知为“填表” | 模板只决定文书结构与格式，案件信息由 AI 自动获取 |
| 起草弹窗同时出现模板、文书类型、请求事项等概念 | 主流程只要求模板；文书类型继承模板，请求事项由任务文本或模板生成 |
| 当前文书提示强调“不追问”，无法区分普通缺字段与关键决策 | 普通缺字段用 `xx`，关键决策通过可恢复的人机暂停主动询问 |
| 打开文书工作台后，中间区从对话切换到文书详情 | 对话保持为主工作区，文书预览在右侧或抽屉中展开 |
| 自定义模板仅支持粘贴文本或读取 `.md/.txt` | 直接上传 `.docx`，保留原文件并尽可能继承段落、表格和页面样式 |
| 已有 AI 修订和版本能力，但任务、消息、当前稿的绑定不够直观 | 每轮修改明确显示“基于 vN 生成 vN+1”，消息可回到对应版本 |

### 1.2 非目标

- 不让 AI 替用户作出最终诉讼立场、认罪、和解、请求变更等决策。
- 不为了“零提问”而编造事实，也不把每一个缺失字段都变成问题。
- 不允许文书任务修改关联案件的材料、OCR、批注或案件记忆。
- 不在首期承诺支持旧版 `.doc`、宏文档或所有复杂 Word 特性的无损编辑。
- 不取消定稿前的人工核实、来源失效检查和正式导出门禁。

## 2. 现有技术架构分析

### 2.1 总体调用链

当前文书生成同时存在固定图流程与自主 Agent Loop 相关实现。实际对话发起通过 `agent.start` 进入 Core，文书专属输入由 `docgenInput` 携带；模板、草稿和导出另有独立 RPC。主要链路如下：

```text
React 首页 / Dock / 发起弹窗
        │
        ├─ agent.start(mode=document_generation, docgenInput)
        │       └─ 自主 Agent Loop / 文书生成图流程
        │              ├─ documents / memory / case_explore：读取案件上下文
        │              ├─ docgen_create_draft：创建草稿
        │              ├─ docgen_render_draft：填槽位、渲染、落盘 Word
        │              └─ docgen_revise_draft：生成 AI 修订版本
        │
        ├─ docgen.* RPC：模板、草稿、槽位、提纲、定稿、版本与导出
        │
Electron preload / IPC
        │
Python Core
        ├─ docgen.py：模板、槽位、正文、版本与导出门禁
        ├─ citations.py：引文规范化、页码与版本核验
        ├─ cases.py：当前任务 + 关联案件的只读可读范围
        └─ SQLite / 工作空间文件：草稿、版本、审计和 Word 产物
```

关键现状：

- [store.ts](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/state/store.ts#L2476-L2504) 在已打开草稿时将后续输入路由为 AI 修订，否则携带当前模板发起新起草。
- [service.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/service.py#L1013-L1131) 已注册模板、草稿、槽位、提纲、渲染和修订等文书 RPC。
- [autonomous.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/agent/autonomous.py#L3534-L3689) 已向 Agent 提供模板查询、建稿、渲染、读取和修订工具，并在渲染或修订后发布 Word 文件卡。
- [graph.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/agent/graph.py#L437-L498) 的固定图流程也包含建稿、案件检索、提纲和正文生成，但部分门禁与自主 Loop 的草稿策略不同，升级时应避免两套流程行为继续分叉。

### 2.2 关联案件与案件上下文

关联案件能力已经落地，不需要重新设计数据归属：

- [index.ts](file:///e:/project/Slvyue%20(2)/packages/contracts/src/index.ts#L85-L115) 的案件契约已有 `linkedCaseId`。
- [NewCaseDialog.tsx](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/components/NewCaseDialog.tsx#L119-L145) 在创建文书任务时允许选择关联案件，并明确只读共享语义。
- [cases.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/cases.py#L190-L221) 通过 `readable_case_ids` 将读取范围限定为“当前任务 + 显式关联案件”，且要求同一工作空间。
- [docgen.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/docgen.py#L736-L765) 校验槽位引证时也使用该可读范围，因此关联案件原文可以成为文书事实来源。

这意味着“AI 先了解关联案件”主要是任务编排和上下文产品化问题，而不是跨案件权限模型问题。

### 2.3 模板、槽位与正文渲染

[docgen.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/docgen.py#L45-L116) 当前支持：

- `{{字段}}` 与 `【字段】` 两类变量；
- `case_evidence / user_confirmed / pending_verify` 三类槽位来源；
- 未填槽位统一渲染为 `xxx`；
- 正文占位符审计；
- strict/reference 两种模板模式。

[DocGenStartDialog.tsx](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/components/DocGenStartDialog.tsx#L148-L194) 目前通过 `FileReader.readAsText` 读取模板，只接受文本内容，并非真正的 Word 模板导入。

[DocGenWorkspace.tsx](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/components/DocGenWorkspace.tsx#L72-L109) 会在选择推荐卡或模板后构造并回填提示词，[Dock.tsx](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/components/Dock.tsx#L374-L380) 再提示用户替换蓝色待填片段。这是“仍需填写基本案件信息”的主要前端来源，应在升级后移除主流程中的这一行为。

### 2.4 引证、版本与导出是应保留的底座

- 案件原文槽位必须带文档、页码和短原文片段，并通过版本与 OCR 质量校验；用户确认的信息与待核实信息分开记录。
- AI 修订已会追加 `ai_revise` 版本，而不是覆盖历史稿；恢复历史版本也不会删除较新版本。
- 存在占位或待核实来源时，不允许直接定稿；含缺失信息的文件可以带“草稿”标识导出。
- [m3_docgen.py](file:///e:/project/Slvyue%20(2)/services/core/evals/m3_docgen.py#L1-L35) 已覆盖模板解析、缺失不编造、来源分类、版本恢复和导出等基础门槛。

因此，新方案应减少的是重复输入和机械确认，不是削弱证据与审计要求。

### 2.5 当前关键缺口

1. **缺少通用的人机问答暂停协议**：契约已有 `WAITING_HUMAN`，但文书生成没有“问题集—回答—同任务恢复”的完整工具、事件、RPC 与持久化卡片。
2. **提问策略与目标相反**：[autonomous.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/agent/autonomous.py#L1577-L1594) 当前要求“不反复确认”且“材料无法确认一律写 xxx、不追问”，无法表达“普通信息不问、必要决策必须问”。
3. **起草入口仍有表单心智**：模板、文书类型、请求事项以及蓝色待填提示同时存在。
4. **对话与文书视图相互切换**：[Center.tsx](file:///e:/project/Slvyue%20(2)/apps/desktop/src/renderer/src/components/Center.tsx#L53-L57) 在打开草稿后以工作台替代中间对话区，不利于持续对话迭代。
5. **Word 模板尚未实现**：当前模板内容模型是 Markdown 文本，没有 DOCX 原件、OOXML 映射和格式保留链路。

## 3. 升级后的产品原则

### 3.1 一个主任务，两种信息处理策略

| 信息类型 | 示例 | 系统行为 |
| --- | --- | --- |
| 普通案件字段 | 姓名、证件号、地址、日期、金额、案号、法院、联系方式 | 先从案件自动提取；无法确认则写 `xx`，继续生成草稿 |
| 必要用户决策 | 我方立场、诉讼地位、主位/备位请求、辩护方向、是否认罪、是否调解、请求金额取舍、是否采用某敏感事实 | 会实质改变文书方向时主动提问；回答写入 `user_confirmed` 决策记录 |
| 来源冲突或质量不足 | 两份材料金额不同、关键页 OCR 低置信度、文档版本失效 | 不自行选择；影响关键结论时询问，否则保留 `xx` 和待核实提示 |
| 表达方式偏好 | 更简洁、更强硬、更正式、压缩某段 | 不阻断首稿；用户可在对话中随时提出并迭代 |

### 3.2 提问少而关键

- 不因模板有空字段就提问。
- 不重复询问关联案件已有明确答案的信息。
- 一次只提出会改变下一步生成行为的问题；可分批，每批建议不超过 3 个。
- 每个问题必须说明“为什么现在需要决定”，选项应具体、互斥且可回答。
- 非关键问题不得阻塞首稿；关键问题未回答时任务进入 `WAITING_HUMAN`，不能假装完成。
- 用户选择“暂不决定”时，只有在能安全地产出多方案或不相关草稿的情况下才继续，否则保持等待并说明影响。

### 3.3 对话是主界面，文书是持续更新的产物

对话负责表达目标、回答决策、提出修改和解释版本；文书预览负责阅读、定位、对比与导出。两者同时可见，不再要求用户在“对话”和“文书工作台”之间来回切换。

## 4. 目标用户流程

### 4.1 首次生成

```text
创建/进入文书任务并关联案件
            │
            ▼
选择模板（文书类型自动继承）
            │
            ▼
可选：补充一句目标或特殊要求 → 发送
            │
            ▼
AI 自动了解案件：案件信息 → 材料 → 记忆/已有分析 → 原文复核
            │
            ├─ 普通信息缺失：记录待补充，正文写 xx
            │
            └─ 发现必要决策：展示问题卡 → WAITING_HUMAN
                                      │
                                      └─ 用户回答 → 从原任务检查点继续
            │
            ▼
生成 v1 草稿 + Word 文件卡 + 来源/待补充摘要
            │
            ▼
用户通过对话修改，或预览、比较、恢复、定稿和导出
```

任务发送时不再要求用户填写案由、当事人、请求事项等基础字段。若用户未输入额外要求，系统可自动生成内部任务描述：

> 请根据当前关联案件的材料与案件记忆，按照已选模板起草《{模板文书类型}》。可从原文确认的信息自动使用；普通缺失信息写 xx；仅在必要决策不明确时向我提问。

该描述用于 Agent 任务，不要求用户编辑，也不必以一大段预填文本占据输入框。

### 4.2 未关联案件的处理

“自动读案”依赖明确关联关系，主流程应引导用户在任务级完成关联，而不是每次发送都重新选择：

- 已关联：直接发送，输入坞显示关联案件只读状态。
- 未关联：发送前显示轻量选择卡：“选择关联案件后开始”或“不关联，空白起草”。
- 空白起草：允许继续，但明确普通信息将更多使用 `xx`；不得伪装为了解了某案件。
- 来源案件被删除：关联置空，历史引用标记 `stale`；已有版本保留，新生成不得继续把旧引用当成有效事实。

### 4.3 对话修订

示例：

- “把事实与理由压缩到 800 字，不改变金额和日期。”
- “采用刚才选择的罪轻辩护方向，强化自首和退赃部分。”
- “第二项诉讼请求改为备位请求，并说明这样修改的影响。”
- “对比 v2 和 v4，恢复 v2 的证据列表，但保留 v4 的结尾。”

每轮修订遵循：

1. 明确当前草稿与基准版本。
2. 只修改用户要求涉及的内容，其他内容保持不变。
3. 新事实必须重新读取原文或由用户明确确认；不能借“润色”增加案件事实。
4. 生成 `ai_revise` 新版本和对应 Word 文件卡。
5. 回复简述修改位置、未解决的 `xx`/待核实项和新增决策。
6. 若当前稿在用户查看后已被手工编辑或其他窗口更新，先提示版本变化，不静默覆盖。

## 5. 主动提问交互方案

### 5.1 参考图转化为应用内问题卡

参考图的核心不是普通聊天气泡，而是嵌入任务流的结构化决策卡。建议保留以下视觉与交互特征：

- 卡片位于对话流底部，宽度受中间工作区约束，采用现有应用的浅色背景、边框、圆角和字体 token。
- 顶部显示问题标题，右侧显示 `1 / 2`、前后切换和关闭/收起。
- 选项采用整行可点击区域；选中态同时使用边框、勾选图标和背景色，不只依赖颜色。
- 每个选项包含短标题与一行后果说明，例如“无罪辩护——需要围绕构成要件与合理怀疑组织正文”。
- 提供“其他”自由输入；必要时提供“暂不决定”，并说明对生成的影响。
- 底部主按钮为“提交并继续”或“下一步”，次按钮为“取消任务”；键盘操作与焦点管理符合现有弹层规范。
- 卡片上方显示简洁状态“文书生成需要你的决策”，不展示模型内部推理过程。
- 回答后卡片转为只读摘要，保留当时的问题与选择，便于审计和版本追溯。

### 5.2 问题卡示例

```text
文书生成需要确认辩护方向                         1 / 2

本案材料同时存在罪轻与无罪的论证空间，选择将影响事实组织和法律分析。
你本起文书希望采用哪种主方向？

● 罪轻辩护（推荐）
  围绕自首、退赃、谅解及量刑情节展开，不否认全部指控。

○ 无罪辩护
  围绕构成要件、证据能力和合理怀疑展开。

○ 主位无罪、备位罪轻
  同时保留两套论证，文书篇幅和审查要求更高。

其他：____________________________________

                         暂不决定    提交并继续
```

“推荐”只能表示 AI 基于现有材料的建议，必须附简短理由；最终选择仍记录为用户决策。

### 5.3 暂停与恢复技术语义

不建议让 Python 线程无限等待前端回答。采用可恢复的显式暂停：

1. Agent 调用 `request_user_decision`，提交问题集、影响说明和当前检查点。
2. Core 校验并持久化问题集，发出 `human_question` 事件，任务进入 `WAITING_HUMAN`。
3. 当前模型调用与工具循环结束，但任务、会话、草稿和问题卡均保留。
4. 前端通过回答 RPC 提交 `questionSetId + answers`。
5. Core 校验问题仍处于待答状态，将答案写为 `user_confirmed` 决策，追加 `human_answer` 事件。
6. 从同一任务检查点恢复，不新建草稿、不重复用户消息、不重复已完成工具副作用。
7. 页面刷新或应用重启后，仍可从任务快照恢复待答卡片。

重复提交同一回答应幂等；任务已取消、问题已失效或草稿版本已变化时，返回明确状态而不是继续执行旧上下文。

## 6. Word 自定义模板方案

### 6.1 用户操作

模板管理提供“上传 Word 模板”，用户选择 `.docx` 后系统自动完成：

1. 保存原始文件到工作空间模板存储，计算 SHA-256；原文件只读保留。
2. 解析正文、表格、页眉页脚、段落样式、编号、页面设置和资源关系。
3. 识别显式变量 `{{字段}}`、`【字段】`。
4. 没有显式变量时，不阻止导入：默认作为“参考模板”，由 AI 识别文书结构、示例字段和可替换内容。
5. 展示导入结果：模板名称、文书类型、识别到的章节/字段数量、格式警告，然后即可选用。

用户无需先编辑字段表。只有会导致固定文字被错误改写的重大歧义，才通过问题卡询问；一般识别不确定时采用 reference 模式并在预览中提示。

### 6.2 两种模板使用模式

| 模式 | 适用文件 | 生成方式 | 固定内容保护 |
| --- | --- | --- | --- |
| strict | 含明确占位变量的 DOCX | 在原 OOXML 上替换变量，未填值写 `xx` | 非变量文字和样式不得被模型改写 |
| reference | 普通范本、带示例案件的 Word、无变量文书 | AI 按原结构与风格生成新正文，再写回模板副本 | 原文件不改；示例内容不得误当新案件事实 |

未显式配置时，系统按“是否存在有效变量”选择默认模式，用户可在模板详情中调整，但不是上传后的必填步骤。

### 6.3 DOCX 技术实现建议

项目已有 [word.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/word.py) 的 Word 模型转换能力，以及 [docxpatch.py](file:///e:/project/Slvyue%20(2)/services/core/lawbuddy/docxpatch.py#L1-L6) 的 OOXML 增量写回思路。模板导入应复用这些能力，新增薄适配层，而不是另起一套办公文档栈。

建议处理原则：

- 以原始 DOCX 字节为格式基底，所有生成结果写入新文件，不覆盖模板原件。
- 对跨多个 run 的占位符先按段落/单元格组合识别，再做最小范围替换，避免仅按单 run 查找导致漏替换。
- strict 模式只修改变量所在文本节点，其余 ZIP 部件、页眉页脚、图片、样式和编号尽量原样复制。
- reference 模式以模板副本为输出基底；无法安全保留的文本框、域、修订记录、内容控件等必须产生明确警告，不得静默丢失。
- 上传文件不进入案件材料库，不改变关联案件文档列表；模板与案件材料的权限和生命周期分开。
- `.doc` 首期提示用户另存为 `.docx`；加密或损坏文件导入失败并保留可理解的原因，不生成空模板。

### 6.4 模板与版本数据需要补充的信息

在现有模板模型上增加或内部记录：

- `sourceFormat: md | txt | docx`；
- 原始文件 blob URI、文件名、SHA-256、文件大小；
- `fieldMapping`：字段与段落/表格/页眉页脚位置的映射；
- `templateMode`、解析状态、格式警告；
- 自动识别结果与识别依据，不将示例人物自动写成新案件事实；
- 每个草稿继续固定模板版本号和内容哈希，模板后续更新不改变历史文书。

## 7. 对话、预览与版本的界面改造

### 7.1 布局

- 左侧栏继续复用其他模式的通用结构，不新增文书专属左栏。
- 中间区固定为对话与任务流，包含进度、问题卡、生成摘要和各版本文件卡。
- 右侧区用于当前 Word/正文预览、来源定位、版本差异和导出操作。
- 窄屏时右侧预览变为抽屉，但对话上下文和当前草稿标识保持可见。
- 现有文书工作台中的有效能力迁入预览工具栏；没有实际交互能力的说明性面板不再恢复。

### 7.2 起草首页与输入坞

- 模板卡只展示名称、文书类型、来源和当前版本，不再显示“重点填写：原告、被告……”。
- 选中模板后仅设置 `templateId/docType`，不调用 `buildDraftPrompt/buildTemplatePrompt` 回填待填文本。
- 输入框提示改为“选模板后直接发送，或补充起草目标与修改要求”。
- 输入坞持续显示三个上下文锚点：关联案件、当前模板、当前草稿版本；它们是状态入口，不是新的必填表单项。
- 发送按钮允许“只有模板、没有额外文本”的任务；前端使用系统默认任务描述。

### 7.3 生成与修订消息

每轮结果建议包含：

- 一句话结果：“已根据关联案件生成民事起诉状 v1”；
- Word 文件卡与“预览”入口；
- `xx` 数量和待核实来源数量；
- 本轮采用的用户决策；
- 必要的来源芯片或“查看事实依据”入口；
- “继续修改”聚焦输入框，而不是再打开完整起草表单。

固定提示“关键事实请以原文为准”继续保留。

### 7.4 版本一致性

- 消息、文件卡、预览和恢复操作都携带 `draftId + versionNo`。
- 手工编辑、自动保存、AI 修订和恢复继续沿用现有版本类型；恢复生成新版本，不删除后续历史。
- AI 修订必须带 `baseVersionNo` 或等价的内容版本锚点，避免基于旧稿覆盖新稿。
- 定稿后再次修订应回到草稿态并重新要求内容核实。
- 关联案件材料版本变化后，相关事实引用进入 `stale/needs_human`，不能仍展示为已支持。

## 8. Core 与共享契约改造建议

### 8.1 案件上下文准备

在文书 Agent 开始生成前形成一次可审计的“案件上下文准备”阶段：

1. 读取关联案件元数据、案件类型、程序阶段和委托方信息。
2. 获取材料清单、解析状态和版本，优先读取与所选文书相关的原文。
3. 检索带源案件来源的记忆、既有阅卷结论和 Claim Ledger；记忆与原文冲突时回原文复核。
4. 形成内部上下文包：已确认事实、主体陈述、冲突、缺口、来源引用、材料版本。
5. 将上下文包与任务检查点绑定，恢复提问后继续使用；发现材料已变化时先重新校验。

该阶段不复制来源案件内容到文书任务，不回写来源案件记忆。文书任务自己的新对话与决策可独立保存。

### 8.2 新增人机问题模型

共享契约建议增加与 UI 无关的通用结构，文书模式先行使用：

```text
HumanQuestionSet
- id, taskId, conversationId, draftId?
- questions[], status, createdAt, answeredAt?
- checkpointId, contextDigest

HumanQuestion
- id, title, reason, kind: single_choice | multi_choice | text
- options[], allowOther, allowDefer
- required, affects

HumanQuestionOption
- id, label, description, recommended?, recommendationReason?

HumanAnswer
- questionId, optionIds[], text?, deferred?

HumanDecision
- questionId, answer, sourceType=user_confirmed
- taskId, draftId?, createdAt
```

答案中只保存决策所需内容；审计 metadata 记录问题 ID、选项 ID、时间和版本，不写入无关案件原文或敏感信息。

### 8.3 RPC、事件与桥接同步更新

建议新增：

- Agent 工具：`request_user_decision`；
- 任务事件：`human_question`、`human_answer`、`task_resumed`；
- RPC：`agent.answer_human_questions`（或等价的统一命名），输入 `taskId/questionSetId/answers`；
- 查询恢复：任务快照包含待答问题集，供刷新和重启恢复；
- 同步修改 Core 注册、Electron 主进程、preload、共享 contracts、前端 store 和评测。

权限审批卡与决策问题卡应复用任务等待生命周期，但保持不同数据模型：审批解决“是否允许工具/外发”，决策问题解决“文书应该如何写”，不能混用。

### 8.4 占位符统一为 `xx`

按新需求，新生成内容的统一缺失标记使用 `xx`：

- 更新 `placeholder_of`、正文审计、预览计数、导出草稿标识和界面文案。
- 过渡期兼容识别既有 `xxx` 与 `【待补充 …】`，历史版本不被批量改写。
- 所有未填槽位都能定位到字段；即使正文只显示 `xx`，内部仍需保留字段级缺失清单。
- 含 `xx` 的草稿可带草稿标识导出，但不能直接定稿为正式文书。

### 8.5 调整 Agent 提示与完成门禁

将当前“一律不追问”改为明确的分流策略：

- 先读取案件，再决定是否需要提问。
- 普通事实缺失写 `xx`，不追问。
- 必要决策不明时调用提问工具，不在最终回答里只留一句“请用户决定”。
- 提问后必须真正暂停；恢复后再生成或修订。
- 完成标准增加：本轮必要决策已回答、当前版本已落库、事实来源已校验、缺失项已列出。
- 固定图流程与自主 Loop 对齐同一语义，避免一个允许未确认提纲直接出草稿、另一个仍被旧门禁阻断。

## 9. 数据安全与证据约束

1. 关联案件始终只读；所有文档、记忆和引证访问继续经过 `readable_case_ids`。
2. `case_evidence` 必须经过文档、页码、原文片段、版本和 OCR 质量校验；用户决策写 `user_confirmed`，缺失写 `pending_verify`。
3. 对叙述性正文，按事实命题绑定一条或多条来源，不要求整段文书必须是某一段原文的子串；但任何金额、日期、主体和关键事实都必须能回到具体原文。
4. 起诉状、供述、证言等来源只能证明“材料如此记载”，不能自动升级为客观事实；文书措辞需与文书类型和立场相符。
5. 来源冲突不得由模型静默二选一；影响文书方向时进入问题卡，否则并列记录并保留待核实。
6. 模板上传和生成日志不记录完整案件正文；文件路径、原文和决策详情不得无边界进入普通日志。
7. 外部模型调用继续沿用现有脱敏、权限和密钥管理边界，新问答恢复不得绕过授权或重复使用失效上下文。

## 12. 主要风险与控制

| 风险 | 控制措施 |
| --- | --- |
| AI 过度提问，重新变成表单 | 问题必须说明对文书的实际影响；普通缺失一律 `xx`；记录并评测无必要提问 |
| 自动读案变成泛泛总结 | 生成前建立带来源和版本的上下文包，关键事实回读原文 |
| 提问恢复后重复建稿或重复导出 | 持久化检查点、工具副作用幂等键、同任务恢复评测 |
| Word 上传后格式丢失 | 原件字节为基底、OOXML 最小修改、格式警告和回读评测 |
| 普通范本中的示例事实污染新案件 | 无变量模板默认 reference；示例内容仅作结构参考，不作为案件来源 |
| 多窗口或手工编辑被 AI 覆盖 | 基准版本锚点、冲突提示、差异查看和显式继续 |
| 为减少步骤而削弱法律可靠性 | 保留来源分类、失效检查、草稿标识和定稿人工确认 |

## 13. 最终建议

本次升级的关键不是再增加一个“文书表单”或“AI 按钮”，而是把现有能力重新组织为一个可暂停、可恢复、可持续修订的任务：

- **模板负责结构与格式；**
- **关联案件负责事实与证据；**
- **用户只负责真正需要人决定的事项；**
- **对话负责目标表达和持续修改；**
- **版本与引证负责可信交付。**

优先完成阶段一的自动读案与主动提问，再做对话/版本同屏和 DOCX 模板，能够最快改善当前体验，同时最大限度复用现有 Core、contracts、引证与版本底座。
